# 차량 접근점과 우회 경로 분석 — 2026-10-14

> 보관 문서: 작성 당시의 조사·변경 기록입니다. 현재 구현·검증 상태는 [문서 목차](../../README.md)에서 관련 문서를 확인하세요. 아래 작업 지시는 이 기록을 열었다는 이유로 실행하지 않습니다.

앱 구현은 변경하지 않고 코드 이력, 연결된 Android 앱의 저장 경로, 공식 API·SDK 문서, 실제 API 요청을 비교했다. 이 조사에서는 입구점 조회 3회와 경로 조회 51회를 수행했다. 키·계정 정보는 기록하지 않았다. 기기 DB의 임시 복사본은 확인 직후 삭제했다.

## 결론

두 문제를 분리해야 한다. 첫째는 경로 옵션 선택이다. 둘째는 목적지 좌표가 어떤 도로에 연결되는가이다. 추천·최단시간·최단거리 비교만으로 둘째 문제가 해결되지는 않는다.

도서관에서 목적지를 약 4.52m 바꾸자 같은 카카오 REST API의 추천 경로가 1,849m에서 1,092m로 달라졌다. 실제 도착 도로도 백양대로501번길에서 백양대로로 바뀌었다. 사용자가 제공한 카카오맵 사진의 1.1km·3분에 가까운 결과를 재현했다. 단, 사진 촬영 당시 GPS·당시 교통을 동일하게 재현한 것은 아니다.

다선초는 기기에 저장된 실제 요청 출발 좌표를 사용했다. 학교 대표 좌표로 요청하면 세 옵션 모두 936m였고 정부 출입구·TMAP 도로명 차량 입구점으로 요청하면 세 옵션 모두 384m였다. 출입구 데이터 자체가 무효한 사례가 아니라, 의미 있는 도착점을 선택해야 하는 사례다.

전국 출입구 파일을 바로 확대하거나 경로 업체부터 교체하기보다, 목적지의 안내용 위치를 결정하는 처리와 SDK 미리보기·안내를 일치시키는 구조를 먼저 고치는 편이 근거에 맞다.

## 도서관 비교

출발은 주례동일1차아파트의 기존 공개 장소 좌표를 고정했다. 목적지는 기존 백양낙조전망대작은도서관의 공개 장소 좌표와, 같은 좌표의 TMAP 도로명 주소에 매핑된 차량 입구점 후보를 비교했다.

| 요청 목적지 | 카카오 옵션 | 거리 | 시간 | 실제 마지막 도로 |
|---|---|---:|---:|---|
| 기존 마커 | 추천 | 1,849m | 345초 | 백양대로501번길 |
| 기존 마커 | 최단시간 | 1,360m | 234초 | 백양대로501번길 |
| 기존 마커 | 최단거리 | 1,360m | 234초 | 백양대로501번길 |
| 도로명 차량 입구점 후보 | 추천 | 1,092m | 196초 | 백양대로 |
| 도로명 차량 입구점 후보 | 최단시간 | 1,092m | 196초 | 백양대로 |
| 도로명 차량 입구점 후보 | 최단거리 | 1,092m | 196초 | 백양대로 |

입력 좌표 차이는 약 4.52m지만 반환된 도로 도착점은 약 39m 남북으로 달랐다. 작은 목적지 좌표 변경이 다른 도로의 연결 지점을 선택하게 만드는 민감도가 실제로 확인됐다. 이것은 '모든 경로 엔진이 항상 직선으로 가장 가까운 도로를 고른다'는 규칙을 입증한 것은 아니다.

`alternatives=true`도 별도로 확인했다. 해당 시점에는 기존 목적지에 대한 경로가 하나만 반환됐고, 도착점은 기존 남쪽 도로 그대로였다. 대안 경로 옵션만 켜서 다른 접근점을 확보할 수 있다는 근거는 나오지 않았다.

부산 정부 자료를 현재 `BusanEntranceService.find()`로 조회하면 이 도서관의 기존 장소 좌표에는 매칭 결과가 없다. 자료를 서버에 보관하고 있어도 마커가 건물군 폴리곤 안에 들어가지 않으면 출입구 보정이 수행되지 않는다. 따라서 데이터 파일이 존재한다는 사실만으로 이 사진의 경로가 정부 출입구 경로였다고 판단할 수 없다.

TMAP 리버스 지오코딩은 같은 지점에 대해 지번 차량 입구점과 도로명 차량 입구점이 다르게 반환됐다. 지번 후보로 카카오에 요청하면 210m가 나왔지만 도로명 후보와 약 63m 떨어진 다른 곳으로 안내했다. 가장 짧다는 이유로 210m 후보를 선택해서는 안 된다. 리버스 지오코딩 응답에 건물명도 없어서 후보가 정확히 같은 시설의 접근점인지 확인하는 절차가 필요하다.

## 다선초 비교

연결된 앱에 남아 있는 2026-10-14 안내 세션에서 `requestedOrigin`을 확보했다. 기록된 목적지는 학교 중심 좌표였고 `destinationSource=original`, 실제 도착점은 학교 북쪽이었다. 저장 경로에는 `navigationDestination`이 없었다. 이 기록은 저장 시점의 상태이며, 서버의 현재 배포 버전이나 사진과 동일한 앱 빌드를 증명하지 않는다.

| 목적지 | 옵션 | 거리 | 시간 | 도착 위치 |
|---|---|---:|---:|---|
| 학교 중심 마커 | 추천·최단시간·최단거리 각각 | 936m | 233초 | 북쪽 도로 |
| 부산 정부 출입구 | 세 옵션 각각 | 384m | 132초 | 자료상 출입구에서 약 8m |
| TMAP 도로명 차량 입구점 | 세 옵션 각각 | 384m | 132초 | 정부 출입구 요청과 같은 도착점 |

카카오 엔진이 정부 출입구 요청을 무조건 이상하게 처리하는 것은 아니다. 이 조건에서는 실제로 짧은 경로가 나왔다. 단, 물리적 현장 통행을 직접 검사한 결과는 아니다.

## 티맵을 쓰면 자동으로 해결되는가

동일한 도서관 출발점·목적지로 TMAP 자동차 경로도 비교했다.

| 목적지 | TMAP 추천 | TMAP 최소시간 | TMAP 최단거리 |
|---|---|---|---|
| 기존 도서관 마커 | 1,335m / 235초 | 1,335m / 235초 | 1,326m / 233초 |
| 도로명 차량 입구점 후보 | 345m / 72초 | 345m / 72초 | 345m / 72초 |

카카오와 TMAP이 동일한 좌표에도 서로 다른 경로를 반환한다. 도로 데이터, 연결 지점 및 탐색 정책이 다를 수 있으므로 엔진 교체가 카카오맵 앱과 동일한 경로를 보장하지 않는다. 345m 경로의 현장 통행 가능성은 이번 조사에서 검증하지 않았다.

도로명 입구점 응답의 도착 옵션을 TMAP 요청에 적용했을 때도 이 사례의 345m 결과는 같았다. 다선초는 중심 좌표에 POI ID와 반환 옵션을 추가해도 457m 경로가 유지됐고, POI 검색이 반환한 입구 좌표를 사용하자 387m였다. '장소 ID만 추가하면 엔진이 반드시 입구 좌표로 바꾼다'는 주장은 이 실험으로 뒷받침되지 않는다.

TMAP의 좌표·입구 종류·POI ID·도착 옵션은 해당 서비스의 규격이다. TMAP의 ID나 옵션 코드를 그대로 카카오 SDK에 전달해서 같은 의미라고 가정하면 안 된다.

## 현재 앱에서 확인된 구조 문제

1. 방문지 마커와 안내용 목적지를 충분히 분리하지 않았다. 정부 자료 조회도 건물 영역 안에 마커가 들어가야 작동한다.
2. 출입구가 여러 개일 때 현재 서비스는 마커와 직선으로 가장 가까운 출입구 하나를 고른다. 출발지에서 가장 빠르게 접근하는 후보를 비교하지 않는다.
3. 이전 `03602ba` 계열 코드에는 마커→출입구 벡터를 10m 연장한 가상 접근점이 있었다. 그 방향이 실제 도로 방향이라는 보장은 없으며 현재는 제거됐다.
4. 현재의 50m 거리 검사는 담·반대편 도로·중앙분리대 여부를 확인하지 않는다. 가까운 잘못된 도로도 통과할 수 있다.
5. 미리보기는 서버 REST 경로이고 안내는 SDK가 별도로 재계산한다. 목적지와 탐색 기준을 같게 넘겨도 경로 전체의 동일성은 보장하지 못한다.
6. 서버 자동 비교는 거리·시간·통행료가 모두 악화되지 않는 후보만 선택한다. 따라서 가장 빠른 경로라도 거리가 더 길면 선택하지 않는다. 사용자에게 '무조건 최단시간'이라고 설명하면 틀리다.

## 가장 먼저 검증할 개선 방향

### 안내용 목적지 처리

장소 마커는 유지하고 안내용 도착점을 별도 필드로 관리한다. 출입구가 있다고 무조건 믿거나 가까운 도로 좌표로 임의 이동하지 않는다. 후보가 해당 시설·주소에 속하는지, 차량용인지, 경로 엔진이 실제로 어느 도로에 도착시키는지 확인한다.

전국 자료를 쓰지 않으려면 알려진 건물 방문지에 대해서만 TMAP 입구점을 필요 시 조회하는 방식이 후보가 될 수 있다. 이번 실험에서는 그 후보를 카카오 REST에 넘겨 도서관과 다선초의 개선을 확인했다. 하지만 잘못된 주소 매칭·누락·도착 옵션 차이 때문에 무조건 성공하는 방법은 아니다. 지도에서 직접 찍은 가로수·노상시설 등의 점을 주변 건물 입구로 자동 변경해서도 안 된다.

### SDK가 계산한 경로로 미리보기와 안내 통일

카카오 SDK가 반환하는 경로의 거리·시간·도착점·폴리라인을 미리보기에 사용하고, 같은 목적지·기준과 SDK의 `KNTrip`을 안내까지 유지하는 구조를 우선 검증한다. 현재 REST 경로를 그려놓고 시작 시 다른 SDK 경로를 요청하는 차이를 줄이기 위한 제안이다.

공식 SDK에는 `routeWithPriority()`의 경로 응답, `KNRoute.routePolylineWGS84()`, 실제 POI 위치 정보 및 재탐색 콜백이 있다. 다만 SDK 후보를 임의 선택해 그대로 안내하는 정확한 구현은 별도 실기기 프로토타입으로 확인해야 한다. 내부 릴리스용 메서드나 비공개 서버 API에 의존하지 않는다.

### 출입구 자료 없이 카카오 SDK만 사용하는 후보

설치된 1.12.8-hotfix02 라이브러리에서 `KNPOIRPFlagType_MP`와 `KNPOI.setRpFlagType()`이 실제로 존재하는 것을 확인했다. 공식 설명상 MP는 목적지 주변 여러 도로를 도착 링크로 허용한다. 이것은 경로 우선순위(TIME/DISTANCE)와 별도 설정이다.

이 옵션을 켜면 단일 도로 도착점의 우회를 줄일 가능성이 있지만, 담 뒤 도로를 제외하거나 정문을 알아내는 기능이라는 근거는 없다. 이번 분석에서는 SDK의 MP 옵션으로 두 장소를 실제 재탐색하지 않았다. 무료이며 완전한 해결책이라고 발표하면 안 된다.

### 검증 순서

1. 도서관과 다선초를 대상으로 SDK만의 기본/MP 도착 옵션, 기존 마커/확인된 입구점, TIME/RECOMMEND를 비교하는 작은 실기기 프로토타입을 만든다.
2. SDK 경로의 실제 도착 도로·마지막 회전·미리보기와 안내의 동일성을 확인한다. 거리·시간 숫자만 짧아졌다고 통과시키지 않는다.
3. SDK 단독으로 해결되면 TMAP 입구점 조회와 전국 파일을 기본 경로에서 제거한다. 해결되지 않는 건물에 대해서만 조회를 사용한다.
4. 인앱 구현보다 카카오맵 앱과 정확히 같은 경험이 우선이라면 카카오맵 앱으로 넘기는 공식 앱 연결을 대안으로 검토한다. 좌표만 넘기는 연결은 장소 검색 선택과 같은 결과를 보장하지 않으므로 장소 식별을 유지할 수 있는 공식 연결 규격을 확인해야 한다.

## 확인 범위와 남은 한계

- 실시간 교통에 따라 시간은 달라진다. API 요청을 짧은 시간에 연속 수행했지만 동일한 교통 스냅샷을 보장하지는 않는다.
- 도서관은 사진 당시 GPS를 확보하지 못했다. 다선초는 기기의 저장 요청 좌표로 재현했다.
- 기존 출입구 파일이 당시 운영 서버에서 로드됐는지는 이번 로컬 조회만으로 알 수 없다.
- 전체 지도 앱들의 비공개 목적지 선택 알고리즘은 공개 문서만으로 확정할 수 없다.
- 실제 SDK MP 재탐색과 실주행, 도서관 입구 후보의 현장 접근 가능성은 아직 검증하지 않았다.
- 앱 소스·서버 소스·설정·설치 앱은 이 분석에서 변경하지 않았다.

## 구현 및 실기기 검증: 2026-10-14

위의 분석 시점 이후 Android 카카오 SDK 1.12.8-hotfix02로 차량 경로 미리보기를 구현하고 실제 기기에서 기본/MP 도착 옵션을 비교했다. 이 절의 결과가 앞의 미검증 상태를 갱신한다.

| 장소 | 도착 옵션 | TIME 거리 / 시간 | RECOMMEND 거리 / 시간 | 마지막 경로 좌표 |
| --- | --- | --- | --- | --- |
| 백양낙조전망대 작은도서관 | SDK 기본 | 1,093m / 192초 | 1,093m / 192초 | 35.1540554, 128.9974973 |
| 백양낙조전망대 작은도서관 | MP | 308m / 72초 | 308m / 72초 | 35.1540460, 128.9975411 |
| 다선초 | SDK 기본 | 387m / 139초 | 387m / 139초 | 35.0630442, 128.9849105 |
| 다선초 | MP | 940m / 240초 | 940m / 240초 | 35.0640839, 128.9856466 |

출발점과 목적지 좌표는 통합 테스트에 고정했다. 출입구 파일이나 TMAP 입구점 조회는 사용하지 않았다. SDK 기본은 도서관에서 사진의 카카오맵 1.1km / 3분과 비슷하게 나오고, 다선초에서는 앞선 출입구 좌표 경로와 가까운 남쪽 도로에 도착한다. MP는 다선초의 북쪽 도로로 바뀌어 오히려 돌아간다. 따라서 MP를 모든 목적지에 켜거나 거리만 비교하여 자동 선택하지 않는다. SDK 내부의 도착점 선택 알고리즘은 이 결과만으로 확정할 수 없다. 도서관 MP 경로의 현장 접근 가능성은 확인하지 않았다.

### 반영한 동작

- 차량 미리보기는 REST 대신 SDK 경로의 거리, 시간, 폴리라인과 실제 차량 도착점을 표시한다. 차량 미리보기의 기본 경로 기준은 TIME이며, 위 실험에서는 RECOMMEND와 같았다.
- 미리보기에서 준비한 `KNTrip`을 메모리에 보관하고 안내 시작 시 같은 객체와 경로 기준을 넘긴다. 안내를 시작할 때 별도의 목적지 보정이나 REST 요청을 하지 않는다.
- 경로는 5분 뒤 만료된다. 만료되거나 출발점에서 30m 이상 움직이면 새 미리보기를 보여준 뒤 다시 시작하도록 한다. 앱 프로세스가 재시작된 경우에도 SDK 경로를 다시 구한다.
- 안내 중 SDK의 재탐색 결과를 앱 경로 상태에 반영한다. 이는 교통 변화나 경로 이탈 후 경로 변경을 막는 기능이 아니다.
- `주변 도로 도착 허용` 비교 옵션을 추가하되 기본값은 꺼짐이다. 장소 마커와 SDK가 계산한 `차량 도착` 위치를 구분한다. 마지막 좌표는 교문이나 보행 가능한 연결을 보장하지 않는다.
- 도보 경로는 기존 방식을 유지한다. 차량 경로의 기본 흐름에 전국 출입구 파일이나 TMAP 조회를 추가하지 않았다.

### 검증 범위

Android 통합 테스트의 8회 실제 경로 요청이 성공했고, 폴리라인, 옵션, 캐시 객체 재사용과 폐기를 확인했다. 화면 회귀 테스트에서는 같은 미리보기 ID로 안내를 시작하는 흐름, 만료 후 갱신, MP 옵션 전달, 재탐색 및 도보 흐름을 검증했다. Android 디버그 앱과 테스트 APK 빌드도 통과했다. 실제 주행, SDK 안내 시작 이후 첫 화면의 경로 일치 및 현장 진입 가능성은 아직 확인하지 않았다.

통합 테스트 실행 방법은 `frontend/scripts/sdk-navigation-probe.gradle`에 기록했다. 이 테스트는 앱 키로 실제 SDK 요청 8회를 수행하므로 반복 실행 시 사용량이 발생한다. 테스트 앱은 검증 후 제거하고 원래 앱과 사용자 데이터는 유지한다.

### SDK 미리보기 교통 색상 수정

SDK 전환 당시 폴리라인의 `x`, `y`만 정규화하고 `trfSt`를 전달하지 않아 차량 미리보기 전체가 회색으로 표시되는 누락이 있었다. 서버나 main 브랜치 반영 여부와 관련이 없다. SDK 좌표의 `trfSt`를 시작점 기준 구간으로 묶어 `trafficSections`로 전달하고, 안내 재탐색 시에도 함께 갱신하도록 수정했다. SDK 통행 불가 값 5는 기존 REST 표시 규격의 6으로 변환한다. 교통 정보를 받지 못한 구간은 회색으로 유지한다. 구간 경계 좌표를 공유해 색상 사이의 누락이 없도록 했다.

수정 후 실기기 통합 테스트 2개가 통과했다. 실제 요청 8회에서 도서관 교통 구간 상태 `[0, 4]`, 다선초 `[0, 3, 0]`을 확인했다. 화면 재탐색 회귀 테스트와 Android APK/번들 빌드도 통과했다. 0 구간은 정보 없음, 4는 원활, 3은 서행이며 화면의 기존 녹색/노란색 표시 규칙으로 전달된다.
