# PANG3 앱 출시 준비 조사 프롬프트

아래 내용을 그대로 실행해 주세요.

---

우리 프로젝트를 실제로 앱 스토어에 출시하려고 한다. 일반적인 출시 체크리스트를 나열하는 데 그치지 말고, 최신 공식 자료와 현재 프로젝트의 실제 코드·설정을 대조해 실행 가능한 출시 준비 보고서를 작성해라. 사용자는 개발·서버·스토어 용어에 익숙하지 않으므로 쉬운 한국어로 설명하되, 판단의 근거는 정확하게 제시해라.

이번 작업은 조사·검증·문서 작성이다. 아래 단계들을 끝까지 수행하고, 완료한 조사와 확인하지 못한 사항을 구분해 최종 결과를 남겨라. 이미 해결된 작업을 다시 미완료로 분류하지 말고, 로컬에서 성공한 것을 운영 출시까지 완료한 것으로 판단하지도 마라.

## 1. 프로젝트와 기존 결정

- 프로젝트 경로: `C:\PANG3-app`.
- 현재 작업 브랜치: `codex/app-release`. 시작 시 실제 브랜치와 변경 상태를 확인해라. 기존 미커밋 변경을 보존해라.
- 모바일은 React Native/Expo 기반이며 Android 네이티브 내비게이션 모듈을 사용한다. 백엔드는 Java/Spring Boot, 보고서 생성은 Python/HWPX, 별도 웹 프로젝트가 있다. 정확한 버전과 사용 범위는 파일로 확인해라.
- 우선 Android/Google Play 출시를 중심으로 조사해라. iOS는 별도 후속 항목으로 정리하고, Android 출시에 필요 없는 iOS 작업을 출시 차단 항목으로 넣지 마라. 공개 출시·제한 배포 방식이 확정되지 않았다면 공개 Play 출시를 조사 기준으로 명시하되 배포 방식에 따라 달라지는 조건을 구분해라.
- AWS는 서버 팀원이 관리하고, 카카오 Developers는 사용자가 관리한다. Google Play 개발자 계정도 사용자가 준비할 예정이다. Expo 계정은 각자 빌드에 사용하는 것으로 이해하고 있으므로, 실제 프로젝트 소유권·서명·업데이트 권한이 어떻게 연결되는지 확인해라. 서로 다른 계정으로 빌드해도 같은 앱을 계속 업데이트할 수 있다고 가정하지 마라.
- 당장은 개인 계정으로 출시를 준비하는 방향이다. 회사 설립이나 조직 계정 전환을 무조건 선행 조건으로 만들지 마라. 개인/조직 계정의 적용 조건과 향후 앱 이전 가능성·제약을 공식 자료로 확인해라.
- 로그인은 아이디·비밀번호 방식이다. 카카오 SDK를 사용한다는 이유만으로 카카오 소셜 로그인을 사용하는 앱이라고 가정하지 마라.
- 로그인 유지, 개인/그룹 업무, 방문지와 보고서, 사진 편집, 지도 검색과 단일 목적지 안내, 업무 이관, 그룹 탈퇴 기록 보존 등을 구현해 왔다. 현재 상태는 실제 코드와 검증 결과로 다시 판단해라.
- 팀장 중심 권한을 제품에 다시 도입하지 마라. 그룹 구성원은 그룹 기록을 조회하고, 수정은 현재 담당자 기준으로 제한하는 기존 결정을 확인해라.
- 그룹 탈퇴 시 남은 업무를 임의의 팀원에게 자동으로 넘기지 않고 기존 기록을 남기는 방향이다.
- 차량 출입구 자동 보정은 사용자 요청으로 철회했다. 기존 카카오 SDK 안내를 유지한다. 정확한 정문·후문 안내를 해결했다고 표현하지 마라.
- 지도 직접선택 UI 디자인 변경은 보류됐다. 현재 지도 중심 선택 동작과 디자인 개선을 구분해라.

기존 문서는 서로 다른 시점의 기록이다. 예를 들어 초기 체크리스트에 인증이 없다고 적혀 있어도 현재 코드에 인증이 구현됐을 수 있다. 최신 코드를 우선하고, 문서의 오래된 판단을 그대로 복사하지 마라. 최신 사용자 수정으로 삭제된 화면이나 문구를 복원하도록 제안하지 마라.

다음을 분리해서 확인해라.

1. 코드에 기능이 있는가?
2. 적절한 테스트가 통과했는가?
3. 실제 기기에서 검증됐는가?
4. 운영 서버·운영 DB에 적용됐는가?
5. 정식 서명된 배포 파일과 스토어 조건까지 충족했는가?

현재 로컬 검증은 H2와 별도 파일 저장 영역, 로컬 API 및 USB 연결을 사용해 왔다. 내장 JS가 있는 로컬 APK도 정식 Play 배포 파일과는 구분해라. Wi-Fi·데이터를 끄더라도 USB로 서버에 연결될 수 있으므로, 이를 완전한 오프라인 테스트로 판단하지 마라.

## 3. 최신 공식 자료를 조사해라

인터넷을 실제로 검색하고 조사일 기준 최신 적용 조건을 확인해라. 블로그나 예전 답변을 결론의 근거로 삼지 말고, Google Play/Android, Expo/EAS, Kakao/Kakao Mobility, AWS, 실제 사용 중인 메일·공공데이터 서비스의 공식 자료를 우선해라. 국내 개인정보 의무는 정부·공식 기관 자료를 우선하고, 해석이 불확실한 부분은 확인 필요로 표시해라.

정책마다 다음을 남겨라: 공식 페이지 제목, 직접 URL, 조사일, 적용 대상과 조건, 프로젝트에 적용되는 이유. 계정 생성 시기·계정 유형·API 수준에 따라 조건이 달라지면 명시해라. 테스트 인원·기간, 심사 기간, 지원 API 수준, SDK 정책, 요금은 기억으로 단정하지 마라. 심사 기간을 확정 일정으로 보장하지 마라.

조사 범위는 다음과 같다.

### Google Play와 Android 배포

- 개발자 계정 생성·본인/조직 인증·연락처·결제 및 계정 상태 확인 사항
- 해당 계정에 적용되는 내부/비공개/공개 테스트 및 프로덕션 접근 조건
- 패키지명, versionCode/versionName, AAB, 업로드 키, Play App Signing, 키 보관 및 계정·앱 이전
- 출시 서명과 카카오 키 해시·허용 앱 등록의 연결
- 목표/최소 API 수준, 실제 네이티브 라이브러리의 ABI·페이지 크기 등 적용되는 호환성 조건
- 위치·백그라운드 위치·카메라·사진·마이크·알림·foreground service 권한과 선언 및 심사 조건. 코드에서 실제 사용하는 권한을 근거로 판단하고 불필요한 권한은 구분
- Data safety, 개인정보처리방침, 앱 접근 권한과 심사용 계정, 계정 삭제의 앱 내부/외부 경로, 콘텐츠 등급, 광고·결제 관련 선언
- 앱 이름·설명·아이콘·스크린샷·그래픽·지원 연락처·지원 국가·배포 트랙 등 제출 자료
- 사전 출시 보고서, 주요 기기 테스트, 크래시/ANR 관측, 단계적 출시 및 업데이트 절차

### Expo와 네이티브 빌드

- 현재 프로젝트의 소유자·프로젝트 ID·EAS 설정·빌드 프로필·환경 변수·자격 증명 상태
- 각자의 Expo 계정으로 빌드하는 운영 방식의 가능 조건과 공동 관리 방법
- 개발/검증/운영 API·키 분리, HTTP/cleartext 제거와 HTTPS 전환
- 현재 서명이 정식 업로드용인지, 테스트용인지
- SDK와 네이티브 모듈 호환성, 필요한 경우 업데이트 방식과 서명·runtimeVersion 제약
- 클라우드/로컬 빌드 중 현실적인 출시 방식과 재현 가능한 정식 빌드 절차

### 서버·DB·파일·보고서 운영

- AWS의 실제 배포 구조는 확인 가능한 범위에서 조사하고, 접근할 수 없는 운영 상태는 미확인으로 남겨라
- HTTPS 도메인, DB 연결 및 변경 적용, 환경 변수/비밀 관리, 방화벽·접근 제한, CORS
- 운영 DB와 파일·사진·HWPX의 영구 저장, 서버 재시작/교체 시 보존, 백업·복원, 용량 및 보관 정책
- 인증·권한·파일 다운로드·계정 탈퇴·이관 동시성·업로드 종류/크기·요청 제한·로그의 개인정보 노출
- Python/HWPX 의존성, 한글 파일명, 병렬 생성·시간 제한·재시도·임시 파일 정리, 실제 배포 환경의 실행 가능성
- 서비스 오류 감지, 로그·메트릭·알림, 운영 장애 대응과 DB/앱 버전 호환을 고려한 복구 절차
- 개발·검증·운영 환경의 분리와 실제 운영 E2E 검증 계획

### 외부 서비스와 데이터

- 실제 사용 중인 지도/검색/길찾기/내비게이션/음성/푸시/보고서 관련 서비스 목록
- 공개 앱 키와 서버 비밀의 구분, 패키지·도메인·서명 제한, 사용량·쿼터·요금·상업 이용·출처 표시 조건
- SGIS 인증 및 행정동 경계 표시의 미설정 상태와 필요한 준비
- 메일 발송 서비스·발신자/도메인 인증·SMTP 또는 API 설정, 이메일 인증·비밀번호 재설정의 공개 HTTPS 페이지와 링크 처리
- 카카오 지도 도착점 품질 같은 공급자 한계와 우리 코드 결함을 구분

### 개인정보와 사용자 운영

- 코드·SDK 기준으로 수집/저장/외부 전송하는 개인정보 목록과 데이터 흐름: 계정, 이메일, 위치, 사진, 음성, 업무 기록, 기기/푸시 정보 등
- 음성이 실제 저장되는지 또는 인식 서비스로만 전달되는지, AI가 실제 활성화되어 있는지 등은 코드로 확인
- 이용 목적, 보관/삭제, 접근 권한, 그룹 공유, 위탁/외부 전송 및 해당되는 동의·고지 검토
- 개인정보처리방침·운영정책·문의 창구·공지 운영·계정 삭제 안내에서 실제로 준비해야 할 내용
- 현재 준비 중 화면을 실제 고객지원 기능이 완성된 것으로 분류하지 마라. 운영자 정보와 연락처를 만들어 내지 마라

## 4. 기능과 출시 품질을 실제로 대조해라

로그인/유지/로그아웃/계정 변경·탈퇴, 개인·그룹 전환, 가입·초대·이관·탈퇴, 조회·수정 제한, 지도 검색·등록·복귀·단일 목적지 안내, 앱 종료 후 복구, 사진 자르기/펜/회전과 이전·이후, 위치 수정, 개인/그룹 보고서 보관함·다운로드, 날짜 변경·자정 미처리 전환, 오프라인 초안·연결 복구, 알림을 점검해라.

필요한 검증은 기존 테스트를 활용해라. 테스트 결과에는 범위와 한계를 적고, 합성 데이터/로컬 테스트/실기기/운영 테스트를 구분해라. 실기기나 운영 환경을 확인하지 않았으면 성공으로 기록하지 마라. 실제 주행 검증을 도구로 수행했다고 허위 주장하지 마라.

결함, 설정 누락, 제품 결정이 필요한 사항, 단순 디자인 개선을 구분해라. 출시 필수 여부는 실제 영향과 정책 근거로 정하고, 작은 디자인 의견을 임의로 출시 차단 문제로 키우지 마라.

## 5. 비용과 역할을 실행 가능한 형태로 정리해라

스토어 계정·서버·DB·저장소·트래픽·메일·지도/경로 API·빌드 등의 비용을 일회성/월 고정/사용량 비용으로 구분해라. 공식 요금 근거와 가정을 남기고, 사용자 수만으로 비용을 단정하지 말고 요청 수·사진 용량·보고서 생성량 등을 함께 가정해라. 정확히 산정할 수 없는 비용은 범위와 추가 확인 사항으로 표시해라.

할 일을 아래 담당자로 나눠라.

- Codex가 현재 저장소에서 구현·검증·문서로 처리할 수 있는 일
- 사용자: 스토어·카카오 계정, 본인 확인, 운영 결정, 문의 주소·정책 승인, 필요한 실기기 업무 검증
- 서버 팀원: AWS·운영 DB·HTTPS·비밀·백업·배포·모니터링·외부 서비스 설정
- 공동 작업: 출시 서명과 키 등록, 정식 빌드, 운영 E2E, 스토어 테스트 및 배포

## 6. 최종 결과물

저장소에 다음 Markdown 파일을 작성하고, 마지막 답변에는 핵심 판단과 파일 링크를 제공해라.

2. `docs/release/APP_RELEASE_ACTION_PLAN.md`: 우선순위별 실행표. 각 행에 상태, 담당자, 작업, 선행 조건, 근거, 완료 기준을 포함. 오늘부터 진행할 순서와 외부 대기 조건을 표시하되 근거 없는 확정 출시 날짜를 만들지 마라.
3. `docs/release/APP_RELEASE_SERVER_HANDOFF.md`: 서버 팀원에게 전달할 준비·설정·DB 변경·배포·백업·운영 검증 항목.
4. `docs/release/APP_RELEASE_OWNER_CHECKLIST.md`: 사용자에게 필요한 계정 준비·스토어 입력·심사용 자료·운영 결정·확인 목록. 무엇을 어디에서 준비하는지 쉬운 말로 설명.
5. `docs/release/APP_RELEASE_VALIDATION_PLAN.md`: 출시 전 꼭 다시 확인할 시나리오와 기대 결과, 계정/기기/네트워크/환경 조건 및 아직 수행하지 않은 검증.
6. `docs/release/APP_RELEASE_SOURCES.md`: 공식 출처 목록과 적용 조건·조사일. 코드 근거는 해당 파일과 줄 번호를 함께 제공.

실행표의 상태는 `완료`, `운영 확인 필요`, `설정 필요`, `코드 수정 필요`, `사용자 결정 필요`, `보류` 등으로 명확히 구분해라. 우선순위는 다음 기준을 사용해라.

- P0: 공개 전에 해결하지 않으면 계정/개인정보/데이터 보호·핵심 동작·필수 배포 조건을 충족하지 못하는 문제
- P1: 출시 품질·안정성·운영 준비에 중요한 문제. 실제 출시 차단 여부를 별도로 판단
- P2: 출시 후 개선 가능한 항목

마지막 답변에서는 다음을 빠짐없이 설명해라.

- 지금 공개 출시가 가능한지, 불가능하다면 무엇 때문인지
- 코드 작업만으로 끝나는 항목과 사람/외부 서비스 준비가 필요한 항목
- 다음 행동의 순서와 담당자
- 추가로 필요한 사용자 정보는 마지막에 한 번에 묶어서 질문
- 조사·검증하지 못한 범위와 다음에 확인할 방법
