# 자체 경로 엔진 현황과 자동추천·도착점 개선안

기준일: 2026-10-26, Asia/Seoul. 기존 연구 문서, 현재 작업 폴더 소스, 저장된 실험 응답 및 공식 공개 문서를 검토했다. 이번 작업은 조사와 문서 추가이며 앱·서버의 경로 공급자를 변경하지 않았다. 과거 실험을 이번에 새 API로 재실행한 것으로 표현하지 않는다. 현재 작업 폴더의 코드 존재와 운영 서버 배포 여부도 구분한다.

## 1. 판단

국내 도로데이터를 우리 앱에 활용할 방법은 있다. 이미 ITS 차량 도로망을 Valhalla로 변환하여 경로를 계산했다. 카카오 지도를 배경으로 자체 계산 결과를 표시하거나, 자체 엔진의 이동시간으로 방문 순서를 계산한 뒤 카카오 SDK로 다음 목적지를 안내하는 구성이 가능하다.

다만 자체 도로망을 카카오의 내부 경로망에 업로드하거나 자체 폴리라인을 그대로 카카오 내비 SDK의 음성·회전 안내 경로로 가져오는 공개 기능은 확인하지 못했다. 지도에 선을 그리는 기능과 내비게이션 경로를 주입하는 기능을 구분해야 한다.

가장 먼저 고칠 것은 **장소 대표점과 실제 안내 도착점의 구분, 출발·도착 도로 연결 검증, 추천과 안내의 입력 조건 일치**다. 알고리즘 변경이나 국내 도로데이터 다운로드만으로 다선초 문제가 해결되지 않는다.

우선 기존 카카오 지도·안내를 유지하면서 도착점과 순서 계산기를 개선한다. 자체 엔진은 별도 비교 실행을 거쳐 차량 추천용 행렬부터 검증하고, 도보망과 내비게이션 전체 교체는 후속 단계로 둔다.

### 순서 비교 수치의 의미

국내 엔진이 고른 순서를 저장된 동일 카카오 시간 행렬로 평가한 결과다.

| 차량 방문지 | 카카오 행렬 최적 순서 | 국내 ITS+Valhalla 순서의 카카오 평가 | 증가 |
|---|---:|---:|---:|
| 5곳 | 52분 14초 | 52분 34초 | 20초 / 0.64% |
| 20곳 | 1시간 59분 51초 | 2시간 05분 46초 | 5분 55초 / 4.94% |

이 결과는 한 고정 표본에서의 순서 품질이다. 자체 엔진 정확도 95.06%, 실제 운행시간 오차 4.94%, 모든 지역 품질 보장으로 해석하면 안 된다. 국내 엔진 자체 시간은 카카오 시간 대비 중앙값 55.62%로 짧았고 실시간·과거 교통도 연결하지 않았다. ETA로 그대로 노출할 근거는 부족하다.

### 문서와 현재 소스 사이의 차이

초기 설계 문서의 ‘운영 추천 로직은 아직 수정하지 않았다’는 작성 당시 설명이다. 현재 작업 폴더에는 후속 코드가 있다.

- `VisitDurationMatrix`: 없는 방향 구간만 수집, 차량 origins/destinations 묶음, 도보 최대 6개 연속 구간 묶음.
- `VisitDurationCache`, `VisitDurationSnapshot`, repository: 사용자·범위·모드별 구간 저장, DB 영속화. 5분 일괄 TTL 구조가 아니며 차량은 안내 시작 시 날짜가 지난 관측값을 제거하는 정책이다.
- `KakaoWalkingClient.durations`: 경유지와 응답 leg별 시간 처리.
- `frontend/utils/recommendationReuse.js`: 완료·삭제 시 상대 순서 보존.
- `VisitOrderService.solve`: 여전히 DP 경계는 12곳이며 CP-SAT 통합은 없다.

따라서 재사용 계층을 처음부터 다시 만들거나, 초기 설계의 13곳 이상 GLS를 확정안으로 취급하면 안 된다. 후속 [솔버 부하 실험](SOLVER_LOAD_BENCHMARK_2026-10-26.md)의 시험 조건에서는 DP 15곳 이하 / 제한 시간 CP-SAT 16곳 이상이 권장됐다. 이는 실제 운영 서버와 도보 표본으로 확정해야 할 후보 분기다.

### 이번 저장 응답 재검사에서 추가로 확인한 출발점 문제

`tmp/domestic-road-comparison/dasun-engine-probe.json`의 입력 출발 좌표와 응답 폴리라인 첫 좌표를 Haversine 거리로 비교했다. 새 외부 요청은 없었다.

| 구성 | 입력 출발점과 경로 첫 점 차이 | 과거 SDK 남쪽 도착점으로 요청했을 때 경로 끝점 차이 |
|---|---:|---:|
| 국내 ITS+Valhalla | 약 96.62m | 약 85.01m |
| OSM+Valhalla | 약 104.25m | 약 22.44m |
| 카카오 REST TIME, 학교 중심 요청 | 약 5.30m | 이 표의 남쪽 도착점 실험 대상 아님 |

따라서 ‘OSM 남쪽 좌표 경로 239m’는 입력 출발점에서 끝점까지 동일하게 연결한 239m라고 단정할 수 없다. 자체 엔진은 목적지뿐 아니라 출발점 연결도 검사해야 한다. 그래프 누락, 접근 규칙, 후보 도로 선택 또는 변환 영향 중 무엇이 원인인지는 이 수치만으로 확정할 수 없다.

국내 엔진의 원래 400구간에서도 시작 또는 끝점 차이가 100m를 넘는 구간이 175개였다. 길찾기 성공률만 보고 공급자를 교체하면 안 되는 이유다.

## 4. 한국 도로정보를 카카오 지도에 활용하는 방법

### A. 카카오 배경지도에 자체 경로 표시

국내 그래프 → Valhalla 경로 좌표 → WGS84 좌표 목록 → 카카오 지도 Polyline/RouteLine 등의 표시 계층으로 연결한다. 카카오 지도 Web API의 Polyline과 Android 지도 SDK의 도형 표시 기능이 공식 제공된다. 선을 그려도 카카오 기본 도로망 자체가 수정되거나 SDK의 안내 엔진이 바뀌는 것은 아니다.

근거: [카카오 Web Polyline](https://apis.map.kakao.com/web/documentation/#Polyline), [Android 지도에 그리기](https://apis.map.kakao.com/android_v2/docs/getting-started/mapdraw/).

### B. 자체 방문 순서 + 카카오 실제 안내

국내 그래프의 이동시간 행렬로 우리 서버가 방문 순서를 결정한다. 다음 방문지의 검증된 안내 좌표를 카카오 SDK에 주고, SDK가 만든 경로를 미리보기와 실제 안내에 사용한다. 지도와 사용자 안내 경험을 유지하며 추천용 외부 호출을 줄일 수 있는 후보 구조다.

자체 엔진과 카카오의 교통·도착점 정책이 다르면 추천 순서는 카카오 기준 최적 순서와 달라질 수 있다. 같은 접근점을 사용하는지 검증하고 선택된 구간의 품질을 별도 평가해야 한다.

### C. 국내 출입구 좌표 + 카카오 경로 계산

건물·시설 소속이 확인된 출입구를 안내 좌표로 사용한다. 기존 다선초 384m 실험이 이 구성이다. 도로망 교체 없이 도착점을 개선하는 가장 작은 변경 후보다. 공공 출입구 점이 현재 개방된 차량용 교문인지 확인하는 절차는 따로 필요하다.

### D. 자체 폴리라인을 카카오 내비 SDK의 안내 경로로 사용

검토한 공개 가이드·레퍼런스에서 임의 GeoJSON/Polyline을 카카오 내부 경로로 가져오는 기능은 확인하지 못했다. 공식 흐름은 `KNPOI` → `KNTrip` → `routeWithPriority` → SDK 안내다. `KNRoute` 생성자가 존재한다는 사실이 외부 폴리라인 변환 지원을 의미하지 않는다.

근거: [주행 설정](https://developers.kakaomobility.com/guide/android-ui/driving.html), [KNRoute](https://developers.kakaomobility.com/reference/android-ui-ref-kotlin/class-KNRoute.html).

자체 경로로 실제 내비게이션까지 운영하려면 위치 매칭, 경로 이탈 판단, 재탐색, 회전 안내·음성·안전 정보·백그라운드 동작 등을 직접 구현하거나 외부 경로를 지원하는 안내 체계를 선정해야 한다. 이 전체를 현재 엔진 연구 완료 범위로 잡으면 안 된다. 기술적 표시 가능성과 각 데이터·지도·외부 API의 실제 서비스 이용조건도 분리해 확인한다.

ITS 교통 API가 부산의 모든 골목길 속도까지 제공한다고 가정하면 안 된다. 제공 링크 커버리지·갱신 간격·누락률을 실제 범위에서 확인해야 한다. 제한속도만 이동속도로 쓰는 문제도 해소해야 한다. Valhalla는 기본속도 외에 실시간 및 과거 교통을 사용하는 구조를 제공하지만, 국내 원본 연결은 우리 작업이다. 최신 문서의 옵션·도구가 설치된 3.9.1에 모두 존재하는지도 버전별로 확인한다. ## 6. 이상한 도착 도로를 줄이려면

### 방문지 데이터 모델

다음 값은 제안하는 새 필드이며 현재 모두 구현된 상태가 아니다.

| 값 | 의미 |
|---|---|
| displayPoint / originalPoint | 업무 마커·검색 대표점. 원래 방문 의도 보존 |
| placeIdentity / buildingIdentity | 공급자 장소ID, 주소, 건물관리번호·건물군 식별자 등 시설 매칭 근거 |
| carAccessPoint / walkAccessPoint | 모드별 검증된 안내 접근점 |
| arrivalEdge / departureEdge | 방향별 도착·출발 도로. 일방통행·진입/출구 차이 표현 |
| source / verifiedAt / status | 출처·확인시각·검증 상태. 임의 confidence 숫자로 사실을 대체하지 않음 |
| manualOverride | 사용자가 선택·확인한 업무용 접근점 |
| endpointVersion | 입구 변경 시 행렬·미리보기 캐시를 함께 무효화할 버전 |

### 결정 순서

1. 방문 의도를 구분한다. 학교 방문과 지도에서 찍은 가로수 점은 다르다. 노상 업무는 주변 건물 입구로 이동시키지 않는다.
2. 시설 정체성을 확인한다. 본교·병설유치원, 같은 이름 지점, 건물군 내 다른 동을 구분한다. 단순 반경 최근접 입구는 확정 근거로 쓰지 않는다.
3. 차량/도보 후보를 나눈다. 차량 진입 제한, 일방통행, 교문 운영시간, 계단·횡단 연결을 표현한다. 모르는 조건은 미확인 상태로 남긴다.
4. 시설과 도로 연결을 검사한다. 담장·하천·중앙분리대·고가/지하 레벨을 가로지르는 가짜 연결을 만들지 않는다. 필요한 미세 연결 도로가 없으면 검증된 원본으로 보강한다.
5. 엔진 요청 후 실제 시작·끝 도로를 다시 확인한다. 좌표 차이만으로 정답을 판정하지 않는다. 30m 안에 있어도 담 뒤라면 실패다.
6. 검증된 후보끼리 이동시간·접근성을 비교한다. 가장 짧은 경로를 먼저 고르고 입구 정체성을 나중에 맞추지 않는다.
7. 미확인 장소는 미리보기에서 실제 도착 위치를 구분해 보여주고, 필요한 경우 사용자가 접근점을 지정할 수 있게 한다. 확인한 수정을 해당 시설·모드에 저장한다.

MP 일괄 활성화, 대표점→입구 벡터 연장, 학교 중심에서 가장 가까운 도로, 최단거리 옵션 일괄 변경은 해결안으로 채택하지 않는다. 과거 사용자 요청으로 철회한 자동보정을 이번 조사만으로 운영에 복원하지 않았다.

Valhalla에는 방향·도로 측면·탐색 범위·교량/터널 등 후보 필터가 있다. 올바른 접근점을 입력한 다음 도로 후보를 통제하는 데 도움을 주지만 교문을 스스로 찾아내는 기능은 아니다. `radius` 등의 값을 곧바로 절대 금지 조건으로 오해하지 않고 설치 버전에서 동작을 확인한다. [Valhalla 위치 옵션](https://valhalla.github.io/valhalla/api/route/api-reference/).

## 7. 자동추천을 어떻게 고칠까

### 7.1 입력부터 통일

추천 행렬, 상세 미리보기, SDK 실제 안내가 같은 시설·모드별 접근점을 사용하도록 계약을 둔다. 현재 추천은 서버 카카오 REST 시간이고 차량 미리보기는 SDK 경로여서 같은 장소 대표 좌표라도 도착 도로가 달라질 수 있다. 첫 목적지뿐 아니라 모든 방문지의 도착·출발 상태가 일치해야 한다.

서로 다른 입구를 구간마다 독립적으로 최소화하면 A→학교는 북문, 학교→B는 남문을 골라 내부 이동을 0초로 취급할 수 있다. 초기에는 장소별 검증 접근점 하나를 고정한다. 복수 입구를 최적화하려면 입구 상태를 순서 계산에 포함하거나 입구 사이 실제 내부 이동 비용을 추가해야 한다. 시간창·작업시간·복귀도 같은 모델에 반영한다.

### 7.2 현재 재사용 코드를 확장

현재 `VisitDurationMatrix`를 살리고 `DurationProvider` 같은 공급자 인터페이스 뒤로 카카오·로컬 Valhalla를 분리하는 안이 적합하다. 이는 제안 이름이며 현재 존재하는 클래스가 아니다.

캐시 식별에는 모드·옵션·방향 좌표뿐 아니라 공급자, 도로망 버전, 접근점 버전, 도착 정책 및 필요한 시간 조건을 넣는다. 오래된 교통 관측으로 계산한 순서와 현재 SDK 예상시간을 동일한 시점 결과처럼 표시하지 않는다. 기존 정책을 무조건 짧은 TTL로 바꾸어 전체 재조회하는 식의 비용 회귀도 피한다.

### 7.3 순서 계산기 교체 후보

- 작은 문제: 정확 DP. 현재 12곳 경계이며 15곳까지 확대 후보는 실제 JVM·동시 요청 조건으로 확인한다.
- 큰 문제: 최근접+2-opt를 유효 초기해로 만들고 제한 시간 CP-SAT 또는 GLS로 개선한다. 동일 행렬에서 더 좋은 유효 결과를 보존한다.
- CP-SAT가 제한 시간에 종료되면 OPTIMAL과 FEASIBLE을 구분한다. 초기해보다 나쁜 결과·해 없음·시간 초과 시 기존 유효해를 반환한다.
- 부하 시험의 동시 계산 상한 2개·CP-SAT worker 1개는 2 CPU 조건의 후보 설정이다. 29곳 DP 전체 할당은 사용하지 않는다.
- 계산기 내부에서는 경로 API를 호출하지 않는다. 고정된 행렬 스냅샷을 읽는다.

### 7.4 비용 절감용 자체 엔진의 단계적 적용

품질 확인 후 검토할 후보는 ‘로컬 전체 행렬 → 여러 순서 후보 → 필요한 후보만 카카오로 검증 → 확인된 후보 중 선택’이다. 20곳 전체 400개 방향값 대신 선택된 순서의 20개 구간만 외부 검증하는 구성이 가능하지만, 후보 수·묶음·재시도에 따라 실제 요청 수는 다르다. 전체 카카오 행렬 기준 최적성을 보장하지 않는다.

서로 다른 순서를 비교할 때는 같은 공급자·접근점·옵션·가급적 같은 교통 관측 조건에서 평가한다. 일부 구간만 카카오로 교체한 혼합 행렬을 전체 카카오 시간 행렬인 것처럼 취급하지 않는다. SDK 최종 도착 도로와 REST 검증 도착 도로의 차이도 별도 검사한다.

## 8. 다른 길찾기 서비스는 어떻게 계산하나

공통으로 참고할 구조는 장소/주소 검색, 출입·도로 연결, 통행 그래프, 비용 모델, 구간 탐색, 행렬, 방문 순서 최적화, 안내를 나누는 것이다. 공개 자료로 확인한 기능과 내부 구현을 구분했다.

| 서비스·엔진 | 공식 자료로 확인한 방식 | 우리 앱에 주는 시사점 |
|---|---|---|
| Valhalla | 방향 있는 도로 그래프, 회전 제약, 계층과 양방향 A*, 모드별 동적 비용 | 이미 구축한 엔진을 살리고 그래프·접근점·시간 모델을 개선할 근거 |
| OSRM 및 데모 사이트 | OSM 그래프 전처리 CH/MLD, Nearest·Route·Table·Match·Trip 분리 | 빠른 행렬과 방문 순서·위치 매칭은 별도 기능. Trip은 휴리스틱 |
| GraphHopper | OSM 기반 엔진, CH 전처리, 방향·비용 모델 처리 | 엔진을 Java로 바꿔도 출입구 누락이 자동 해결되지는 않음 |
| openrouteservice | GraphHopper 파생 엔진, OSM, Directions·Matrix·Snap; 별도 검색·최적화 서비스 구성 | 다른 경로 사이트도 지도·검색·계산기·최적화기를 조합하는 사례 |
| Google Routes | 좌표 외 Place ID·주소·navigation point 입력. 좌표가 접근 불가능한 인접 도로로 붙을 수 있음을 공식 설명 | 시설 ID·접근점 보존이 중요. 한국 공급자 교체 추천을 뜻하지 않음 |
| NAVER Directions | 실시간 교통, 목적지 좌표 후보 최대 10개 중 비용이 적은 목적지 선택 | 사전에 검증된 입구 후보의 비교 기능을 참고할 수 있음. 비공개 탐색 알고리즘은 단정하지 않음 |
| TMAP | 경로안내·경유지 최적화 분리, reverse geocoding의 navType으로 차량/보행 입구점 제공 | 중심점과 진입점 구분을 참고. TMAP ID·rpFlag를 카카오 규격으로 간주하지 않음 |
| 카카오 | POI 좌표/주소/ID/옵션과 SDK trip 기반 안내. 주소·좌표 충돌 시 좌표 우선 | 이름·주소만 넣으면 잘못된 대표 좌표가 자동 교정된다고 보장할 수 없음 |

초기 검증은 표본 수와 지역·시간대 범위를 미리 고정하고, 출발·도착 연결 오차, 잘못된 시설 도착, 통행 제약 위반, 경로 실패, 카카오 평가 순서 비용, 실제 이동 기록 오차, 요청 수·비용·지연을 분리해 측정한다. 운영 승격 수치 기준은 표본 검증 전에 정한다. 단일 400구간 결과로 전국 배포 품질을 주장하지 않는다.

## 10. 이번 확인의 범위

- 기존 연구 8개와 과거 안내·철회 기록, 현재 추천·캐시·SDK 소스를 읽었다.
- 다선초 저장 응답의 시작·끝 좌표 차이와 부산 출입구 파일의 건물군 수를 읽기 전용으로 재검사했다.
- 카카오·Valhalla·ITS·주소정보·Google·NAVER·TMAP·OSRM·GraphHopper·openrouteservice의 공개 공식 자료를 확인했다. ITS 자료실과 일부 주소정보 상세 화면은 웹 수집에 실패해, 기존 로컬 원본·카탈로그 기록과 접근 가능한 공식 자료를 함께 사용했다.
- 로그인·신청·현장 조사·새 유료 경로 요청·실기기 재실행·운영 배포는 이번 결과의 근거에 포함되지 않는다.
- 연구용 원시 결과는 `tmp/`에 있으므로 장기 재현 자료로 승격할 때 입력·요약·체크섬·버전을 별도 보존해야 한다. 대용량·공급자 원본의 재배포는 각 이용조건에 맞춰 결정한다.
