# PANG3 FairDay 발표 참고자료 조사

조사일: 2026-10-20 / 목적: 발표자료를 만들기 전 사례·구성·시연·발표법을 수집한다. PPT·포스터·발표 대본의 확정본은 만들지 않았다.

## 먼저 읽을 결론

사용자의 방향 교정을 반영한다. PANG3의 발표는 **전체 업무 워크플로우를 먼저 이해시키고, 카카오 SDK 기반 실제 내비 안내·그룹 협업·업무 이관을 핵심으로 설명한다.** 사진·메모·보고서는 업무를 완결하는 지원 기능으로 다룬다. 앞선 조사에서 현장 기록과 보고서 연결에 비중을 치우친 부분을 수정했다.

발표의 중심 문장 후보: **PANG3는 팀의 외근 업무를 함께 관리하고, 담당 방문지까지 앱 내 실제 내비 안내로 이동하며, 담당자가 바뀌어도 기존 업무를 이어받을 수 있게 하는 외근 협업 앱이다.**

세 기능을 모든 경쟁 제품에 없는 독점 기능으로 단정하지 않는다. 현재 확정한 것은 우리 작품에서 강조할 핵심과 차별화 방향이다. 다른 앱과의 우열은 같은 업무 시나리오로 비교 조사해야 한다. FairDay 공식 심사 기준과도 구분한다.

### 먼저 설명할 전체 워크플로우

1. **업무 준비:** 개인 또는 그룹 업무공간에서 방문지와 할 일을 등록·확인한다. 그룹에서는 구성원과 담당 업무·진행 상태를 확인한다.
2. **방문 계획:** 담당 방문지와 우선순위를 확인하고 이동 계획을 정한다.
3. **현장 이동:** 방문지를 목적지로 삼아 **카카오 내비게이션 SDK 기반 앱 내 길안내**를 시작한다. 경로선 표시뿐 아니라 현재 위치에 따른 주행 안내를 제공하는 점을 설명한다.
4. **현장 업무:** 방문지에서 처리 상태를 갱신하고 사진·메모 등 작업 기록을 남긴다.
5. **팀 협업:** 그룹 작업현황에서 구성원의 업무와 진행 상황을 확인한다.
6. **필요할 때 업무 이관:** 본인 담당 업무를 팀원에게 요청하고, 상대가 수락하면 담당자가 바뀌어 이어서 수행한다. 거절하면 기존 담당자가 유지된다. 매번 거쳐야 하는 필수 단계가 아닌 상황별 분기다.
7. **업무 마무리:** 기록을 확인하고 보고서를 생성·다운로드한다.

현재 구현 범위 확인: `TaskTransferService.java`는 완료 업무를 이관 대상에서 제외하고, 행정동 기준 조회 또는 선택한 방문지 ID 목록으로 요청을 만든다. ‘완료 업무를 포함한 행정동 전체가 항상 이동한다’는 과거 요구사항을 현재 기능으로 설명하지 않는다. 이관은 기존 Task의 담당자를 변경하는 구조이며 사진·보고서의 실제 수신자 조회는 시연 전 별도 확인한다.

### 핵심 기능 세 가지와 발표에서 입증할 내용

| 핵심 | 사용자에게 주는 가치 | 발표에서 보여줄 증거 |
|---|---|---|
| 카카오 SDK 기반 실제 내비 안내 | 정한 방문지까지 실제 이동을 안내 | 앱 내 안내 시작, 차량 위치·회전 안내·잔여 거리/시간, 검증된 범위의 음성·재탐색 |
| 그룹 협업 | 개인의 외근 업무를 팀의 담당·진행 현황으로 함께 관리 | 같은 그룹의 두 계정, 작업자별 업무·진행 상태 확인 |
| 업무 이관 | 다른 팀원이 기존 업무를 이어서 처리 | A의 요청 → B의 수락 → 담당 업무 변경 → 기존 기록 조회 → B의 후속 처리 |

카카오 SDK가 제공하는 길안내 엔진과 PANG3가 구현한 업무·화면 연결을 구분한다. Android 코드·지도 전환 문서에서 `KNGuidance`와 앱 내 `KNMapView` 연결을 확인했다. 실제 이동 GPS·음성·이탈 재탐색의 실주행 검증 여부는 별개이며, 구현 존재를 현장 검증 완료로 확대하지 않는다.

추천 참고 순서:

1. 국내 졸업작품의 실제 형식: **외국민 최종발표 PDF**. 화면 소개, 기술 설명, 평가, 부록의 배치를 본다.
2. 우리와 가까운 업무 맥락: **FixMyStreet Wallonie 발표 PDF**. 위치 기반 업무와 담당 부서 연결을 설명하는 형식만 참고한다. 실제 내비·그룹 협업·수락 기반 이관을 대신하는 사례는 아니다.
3. 보조 기능의 시연 참고: **Simpro–SafetyCulture 데모**. 현장 입력과 결과 문서의 연결 형식을 참고한다. 보고서를 PANG3의 대표 차별점으로 삼기 위한 근거는 아니다.
4. 장표 설계: **YC의 슬라이드 디자인 가이드**. 복잡한 화면을 관객에게 어떻게 보여줄지 참고한다.
5. 발표 전달: **YC의 데모데이 발표 가이드**. 말하기·연습 방법을 참고한다.

원문 링크와 접근 상태는 [참고자료 목록](PRESENTATION_REFERENCE_INDEX.md)에 모았다. 아래에서 ‘관찰’은 원문에서 확인한 내용, ‘적용’은 PANG3를 위한 제안이다. 영상은 재생 전체를 시청·청취한 것이 아니라 제작자의 공개 설명과 챕터를 확인한 경우 이를 명시했다.

- [2022년 행사 발표 PDF](https://mobilite.wallonie.be/files/velo/Colloque%20WC%206%20mai%202022/presentations/Fix-my-street-alan-bouvy.pdf)
- [발표가 게재된 행사 페이지](https://mobilite.wallonie.be/home/politiques-de-mobilite/wallonie-cyclable/colloques/journee-wallonie-cyclable---6-mai-2022.html)

관찰: 표지에 실제 현장을 촬영하는 휴대폰 사진을 크게 둔다. 7쪽은 위치·사진·분류가 있는 신고를 모으고 적절한 부서로 전달하는 역할을 설명한다. 8쪽은 이용자 증언을 제목으로, 9쪽은 개선사항, 10–12쪽은 이용·처리 관련 그래프를 제시한다. 일부 그래프는 한 장에 정보가 많다.

적용: PANG3 표지나 문제 설명에 추상적인 기술 이미지보다 **시설물·현장 기록·완성 보고서**가 어울린다. 담당자 변경은 이름 변경만 보여주기보다 사진·메모·상태·보고서가 함께 이어지는지 보여준다. 다만 시민 신고 서비스와 직원의 업무 수행 도구는 사용자가 다르므로 동일 서비스로 설명하지 않는다. 이 자료의 기관 소개 분량과 많은 그래프를 그대로 복사하기보다, 우리에게 필요한 현장 사례와 증거만 고른다.

### C. SyncEzy의 Simpro–SafetyCulture 연동 데모 — 입력에서 보고서까지

- [제작자 공개 영상·챕터](https://vimeo.com/860917460)
- 확인: 제작자가 올린 설명·타임스탬프. 영상 전체 재생·청취 및 발성·동작 평가는 하지 않았다.

관찰: 설명에 따르면 01:46에 연동 흐름, 02:16에 데이터 연결, 03:06에 기능, **04:16에 실제 데모**, **05:40에 점검 보고서**, 07:06에 데이터 반영을 다룬다. 방문 업무의 정보가 현장 점검과 결과 문서로 이어지는 순서다.

적용: 가장 참고할 구간은 **04:16–07:06**. PANG3는 ‘보고서 생성 버튼이 있다’에서 멈추지 않고, 방금 기록한 사진·위치·메모가 실제 HWPX의 어디에 들어갔는지 연결해서 보여주면 좋다. 해당 서비스의 연동·자동화 범위를 우리 구현처럼 말하지 않는다. 제품 교육용 데모 전체 길이를 짧은 심사 발표에 그대로 옮기지도 않는다.

### D. 우아한테크코스 ‘요즘카페’ 1차 데모데이 — 구체적인 사용자와 핵심 행동

- [팀원이 공개한 발표 준비 회고·슬라이드 이미지](https://solo5star.dev/posts/48/)
- 확인: 작성자 본문의 사용자 정의·발표 준비·데모 설명. 모든 원본 장표·최종발표·실제 발표 영상은 확인하지 않았다.

관찰: 대상 지역을 성수동으로 좁히고, 사용자 인물과 이용 목적을 구체화한다. 핵심을 카페 탐색으로 정하고, 초기 데모는 모킹 데이터로 스크롤하는 수준이었다고 명시한다. 부가 기능보다 핵심 경험 전달을 우선한 사례다.

적용: ‘모든 외근자’보다 **시설물 점검 업무를 받은 사하구 현장 담당자**처럼 한 사용자의 한 업무를 정한다. 시연에는 로그인·설정을 길게 넣지 말고 업무가 시작되는 상태로 진입한다. 이 사례는 초기 스프린트이므로 FairDay의 완성도 증거 수준을 그대로 낮추는 근거로 쓰지 않는다. 우리 시연의 사전 입력 데이터와 실제 수행 구간도 구분한다.

### E. 우아한테크코스 ‘괜찮을지도’ — 지도를 사용자 행동으로 설명

- [팀 공식 프로젝트 소개](https://github.com/woowacourse-teams/2023-map-befine)

관찰: 지도를 만들고, 핀에 이름·생각·사진을 기록하고, 다른 사람과 함께 채우거나 공유하는 행동으로 서비스를 소개한다. 산책 지도와 카페 지도를 함께 보는 식의 사용 예시가 있다.

적용: PANG3에서도 ‘지도 API·그룹 CRUD’보다 ‘어디를 방문해야 하는지 보고, 기록을 남기고, 다른 담당자에게 이어준다’고 설명한다. 이 사례는 **서비스 소개 문장 참고용**이다. PPT 배치나 발표 순서를 확인했다고 해석하면 안 된다.

관찰: Dev Mode·변수·프로토타이핑을 각각 나열하면서도 디자인에서 개발까지 이어지는 변화라는 공통 방향으로 묶는다. 각 기능은 사용하는 팀이 겪는 문제와 연결한다.

적용: 전체 워크플로우로 서비스 맥락을 설명한 다음, **실제 내비 안내·그룹 협업·업무 이관**이라는 세 핵심을 중심으로 묶는다. 사진·메모·보고서는 이 핵심 흐름을 지원하는 기능으로 둔다. 대형 출시 행사의 긴 비전·회사 소개·다수 발표자 구성을 졸업작품전에 그대로 적용할 필요는 없다.

## 4. 사례를 PANG3에 적용하면 PPT는 어떻게 보이면 좋을까

아래는 제작 확정안이 아니라 나중에 장표를 고를 때 쓸 기준이다.

| 전달할 내용 | 어울리는 화면 구성 | 설명할 핵심 |
|---|---|---|
| 어떤 서비스인가 | 실제 앱 화면 1개 + 한 문장 | 누구의 어떤 업무를 돕는가 |
| 기존 업무의 불편 | 방문지·현장사진·문서가 이어지는 기존 절차 | 실제 인터뷰로 확인한 불편이 무엇인가 |
| 사용 흐름 | 방문 준비 → 현장 기록 → 인계·보고 | 기능이 어떻게 이어지는가 |
| 실제 내비 안내 | 업무 방문지 선택 → 앱 내 주행 안내 화면 | SDK 안내가 외근 방문 업무와 어떻게 연결되는가 |
| 그룹 협업 | 같은 그룹의 작업자별 담당·진행 상태 | 팀원이 서로의 업무 상황을 어떻게 확인하는가 |
| 지도·방문 순서 | 동일 방문지의 비교 지도 | 어떤 조건·기준으로 순서를 정하는가 |
| 현장 기록 | 사진·위치도·메모 중 중요한 부분 확대 | 사무실에서 다시 입력해야 할 정보가 어떻게 남는가 |
| 업무 이관 | 보내는 사람·받는 사람 화면과 보존 데이터 | 담당자가 바뀌어도 무엇이 이어지는가 |
| 보고서 | 입력 화면과 완성 HWPX의 대응 영역 | 현장 기록이 최종 문서에 들어갔는가 |
| 현장 피드백 | 요청 → 수정 전후 → 재확인 상태 | 실제 사용자의 요구로 무엇이 바뀌었는가 |
| 기술적 기여 | 선택한 문제 1개, 원인·해결·검증 | 외부 API 연결 외에 팀이 해결한 것은 무엇인가 |
| 검증 | 과제·조건·횟수·결과를 붙인 표나 그래프 | 주장을 어떤 시험으로 확인했는가 |

구체적인 디자인 판단:

- 제목을 ‘보고서 기능’ 대신 ‘현장 기록을 HWPX 보고서로 연결합니다’처럼 메시지로 쓴다.
- 휴대폰 화면은 핵심 1개를 크게, 비교가 필요하면 전후 2개만 둔다. 여러 개가 꼭 필요하면 읽어야 하는 부분을 따로 확대한다.
- 지도는 점·행정동 색·경로를 한꺼번에 빽빽하게 넣기보다 지금 설명하는 대상을 강조한다.
- 전후 비교는 같은 크기·같은 업무 조건을 사용한다. 예전 UI와 현재 UI의 차이인지, 외부 업무 방식과 앱의 차이인지 밝힌다.
- API 로고·기술 스택은 기술적 선택의 이유와 함께 쓴다. 개수 자체는 개발 성과가 아니다.
- 사진·도표·화면은 ‘이 장표의 주장을 증명하는가’로 선택한다. 원본 이미지·다른 팀 디자인은 참고용이며 우리 제품 화면처럼 쓰지 않는다.
- 발표용은 현장에서 읽기 쉬운 큰 화면과 짧은 문장, 보충 근거는 부록에 둔다. 글자 크기는 실제 강의실 투사 상태에서 확인한다.

## 5. 시연은 기능 메뉴 순서보다 업무 순서로

추천 가상 상황: **같은 그룹의 A·B가 외근 업무를 확인한다. A가 자기 방문지로 실제 내비 안내를 시작해 업무를 수행하다가, 남은 업무를 B에게 이관한다. B가 수락하고 기존 기록을 확인해 업무를 이어간다.** 실제 업무의 관찰 결과가 아니라 핵심 세 기능을 설명하기 위한 시연 예시다. 최종 시연 범위는 실제 기기에서 확인된 기능으로 정한다.

| 장면 | 보여줄 결과 | 발표자가 설명할 관점 |
|---|---|---|
| 1. 그룹 협업 | 같은 그룹의 A·B와 담당 방문지·진행 상태 | 팀에서 누가 어떤 일을 맡고 있는지 |
| 2. 실제 내비 안내 | A의 방문지 선택 → 앱 내 안내 시작 | 정한 업무 장소까지 어떻게 이동을 안내하는지 |
| 3. 현장 기록 | A가 남긴 사진·메모·상태 | 다음 담당자가 이어받을 업무 맥락 |
| 4. 업무 이관 | A의 요청 → B의 수락 → 담당 변경 | 인수인계가 실제로 성립하는 과정 |
| 5. 업무 이어받기 | B의 기존 기록 조회·후속 처리 | 단순 공유를 넘어 업무를 이어가는 결과 |
| 6. 마무리 | 완료 기록·필요한 보고서 | 보조 기능이 업무를 어떻게 완결하는지 |

시연 시간은 핵심 세 기능을 읽을 수 있는 길이로 리허설하며 정한다. 그룹·내비·이관에 우선 배분하고 사진·보고서 등 보조 기능은 짧게 연결한다. 이전 제안처럼 이관을 주 시연에서 빼거나 보고서 중심으로 압축하지 않는다. 주행 장면은 실제 기기에서 확인한 녹화를 활용할 수 있으며 정지 시연·주행 영상·실시간 조작을 구분해 표시한다.

시연 준비 방식:

- 로그인과 기본 데이터 등록은 사전에 끝낸다. 미리 준비한 값이라는 점을 숨기지 않는다.
- 실제 GPS 이동은 강의실에서 재현이 어려우므로 경로 생성과 위치 입력을 구분한다. 영상·재현 데이터라면 표시한다.
- 화면 녹화를 쓸지 실시간 조작을 쓸지는 행사 허용 방식과 안정성으로 결정한다. 녹화는 우리 앱 실제 동작으로 만들고 최종 파일에서 재생을 확인한다.
- 실시간 조작을 택하면 같은 흐름의 로컬 영상·정지 화면을 복구 수단으로 준비한다. 외부 접속이 끊겨도 핵심 설명을 이어갈 수 있어야 한다.
- 보고서는 생성 버튼으로 끝내지 않고 실제 파일을 열어 입력과 결과의 대응을 보여준다.
- 사진·음성·동기화·서버 대기시간을 편집으로 줄였다면 실시간 속도처럼 주장하지 않는다.

## 6. 15분에 맞춰 준비할 때의 잠정 비중

발표와 시연 10분, 질문 5분을 가정한 준비용 예시다. 전체 슬라이드 수보다 설명 시간을 먼저 맞춘다.

| 구간 | 시간 | 목적 |
|---|---:|---|
| 서비스 한 문장·사용자 문제 | 0:00–1:20 | 누가 왜 필요한지 이해 |
| 전체 업무 흐름·차별점 | 1:20–2:10 | 해결 방식 파악 |
| 핵심 시연 | 2:10–4:10 | 실제 동작 확인 |
| 팀의 기술적 해결 1–2개 | 4:10–6:10 | 직접 개발한 깊이 전달 |
| 현장 피드백·개선 전후 | 6:10–7:40 | 문제를 현실에서 확인한 근거 |
| 검증 결과·적용 한계 | 7:40–9:10 | 성과와 범위 판단 |
| 팀 기여·다음 검증·핵심 가치 | 9:10–10:00 | 작품의 현재 위치 정리 |

기존 중간발표 구성은 8–10월 개발 과정과 현장 미팅·피드백 반영을 중심으로 한다. 그 내용은 재사용할 수 있지만, 처음 보는 심사위원을 위해 사용자 문제와 현재 동작을 앞에 두는 편이 낫겠다. 월별 개발 일정은 본문에서 짧게 줄이거나 부록으로 옮긴다. 중간발표 원본은 이번 조사에서 수정하지 않았다.

## 7. 실제 발표는 어떻게 진행할까

아래는 가이드와 사례를 바탕으로 한 PANG3용 권장 방법이다. 특정 발표 영상을 듣고 발성·몸짓을 판정한 내용은 아니다.

1. **한 명이 이야기의 흐름을 맡는다.** 다른 팀원은 시연 조작과 분야별 질문을 맡을 수 있다. 주최 측 역할 규칙이 생기면 그 규칙을 우선한다.
2. **화면의 버튼 이름보다 업무 결과를 말한다.** ‘여기를 누릅니다’만 반복하지 않고 ‘이제 다음 담당자가 같은 사진과 메모를 볼 수 있습니다’라고 설명한다.
3. **결과가 나타나는 순간 말을 잠깐 멈춘다.** 보고서나 이관 결과를 관객이 확인할 시간을 준다. 핵심 부분에만 포인터를 사용한다.
4. **기술 설명은 문제·선택·검증의 세 문장으로 준비한다.** 원인을 길게 설명하다가 사용자 효과를 빼먹지 않는다.
5. **전체 문장 암기보다 각 구간의 메시지와 전환을 익힌다.** 첫 문장, 데모 전후 전환, 마지막 핵심 문장은 특히 안정적으로 준비한다.
6. **팀 밖 사람에게 들어보게 한다.** ‘이 앱을 누가 왜 쓰는지’, ‘직접 해결한 기술 문제는 뭔지’를 듣고 말해보게 한다. 기억하지 못하면 내용을 줄이거나 순서를 바꾼다.
7. **녹화해서 시간과 시선을 확인한다.** 화면을 등지고 읽는 구간, 설명이 겹치는 구간, 말을 너무 빨리 하는 구간을 고친다. 영상·파일 여는 시간도 전체에 포함한다.

질문에는 **핵심 답 → 확인한 근거 → 남은 범위** 순서로 답한다. 모르는 수치를 즉석에서 만들지 않는다. 질문을 받은 사람이 내용을 정리한 뒤 필요한 담당자에게 넘기고, 여러 명이 동시에 답하지 않는다.

## 8. PANG3에서 미리 확보하면 좋은 발표 근거

새로운 기능을 늘리기보다 다음 증거를 남기면 발표 준비에 도움이 된다. 지금 즉시 수행하라는 개발 작업 지시는 아니다.

| 모을 자료 | 쓸 수 있는 주장 | 기록할 조건 |
|---|---|---|
| 현장 미팅 원본 메모·사용 허용된 사진 | 실제 업무 요구를 들었다 | 날짜·참여 역할·발언 맥락 |
| 피드백 2–3개의 전후 화면 | 요구를 실제 제품 변경으로 연결했다 | 요청·수정·현재 동작·재확인 여부 |
| 동일 업무의 작업 기록·소요시간 | 해당 시험 조건에서 단계나 시간이 줄었다 | 비교 기준·동일 입력·기기·참가자·횟수·실패 |
| 경로 계산 비교 | 특정 기준에서 방문 계획이 달라졌다 | 같은 방문지·출발지·이동 방식·우선순위·거리/시간 |
| 이관 전후 데이터 확인 | 인계 후 기록이 유지된다 | 상태·사진·메모·보고서·담당자·수락/거절 |
| 실제 생성 HWPX와 입력 기록 | 기록과 문서 결과가 연결된다 | 누락·이미지·위치도·다운로드·열람 결과 |
| 기기 시연 녹화·API 응답 기록 | 확인한 버전에서 흐름이 동작한다 | 빌드·서버·일시·환경 |
| 사용자 평가 원본 | 특정 대상의 반응을 받았다 | 대상·수·질문·좋은 점과 불편한 점 |

시간 비교는 같은 과제를 같은 완료 기준으로 수행한다. 연습 효과와 작업 순서를 기록하고, 소수의 팀원 실험이면 ‘팀 내부 시험’이라고 쓴다. 평균만 제시하지 말고 시도 수·편차·실패도 남긴다. 실험 결과가 생기기 전에는 ‘몇 % 단축’ 같은 값을 넣지 않는다.

현재 자료를 해석할 때 주의할 점:

- 저장소의 기존 발표 제작 소스에는 **2026-10-01 사하구청 미팅**이 기록돼 있다. 미팅 자체와 사용성 개선 효과의 입증은 별개다. 원본 메모와 재확인 기록을 연결하면 더 강한 근거가 된다.
- `ai/app.py`에는 조사 시점에 `ENABLE_AI_ANALYSIS = False`가 있다. **HWPX 생성과 AI 사진 분석을 구분**하고, AI 분석이 현재 핵심 동작이라고 말하지 않는다.
- `RouteService.java`는 우선순위를 반영하고 가까운 방문지를 순차 선택하는 부분을 포함한다. ‘항상 전역 최단 경로’처럼 확대하지 않는다. 선택한 비교 기준을 구체적으로 보여준다.
- 과거 빌드 성공·로컬 테스트·출시 준비 문서는 현재 운영 서비스와 실사용 성과를 증명하지 않는다. 앱 공개 출시·구청 도입 여부는 별도 확인한다.
- 데이터 저장 최소화라는 과거 요구가 있어도 ‘서버에 개인정보를 저장하지 않는다’고 자동 해석하지 않는다. 실제 구현 흐름을 기준으로 답한다.

## 10. 포스터와 발표자료는 역할이 다르다

공고에서 전시 포스터와 발표 PPT는 별도 제출물이다. 이번에는 포스터 양식 첨부파일을 확보하지 않았으므로 크기·항목·배치를 확정하지 않는다.

포스터는 혼자 읽는 사람이 사용자·문제·해결 흐름·핵심 화면·검증 근거를 파악할 수 있어야 한다. 발표 PPT는 발표자의 말과 시연을 따라가도록 장면별로 나눈다. 발표 장표 여러 장을 작게 붙여 포스터로 쓰기보다, 양식을 받은 뒤 전시 거리에서 읽힐 정보부터 고른다.

나중에 포스터를 준비할 때 외국민 공개 폴더의 포스터와 최종발표를 나란히 비교할 수 있다. 이번 조사에서는 해당 팀의 **포스터 파일 존재만 확인**했으며 포스터 내부까지 분석하지 않았다.
