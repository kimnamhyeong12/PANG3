# 자동추천 구간 재사용 구현 (2026-10-26)

자동추천 UI와 기존 순서 계산기(DP 12곳 이하, 이후 최근접+방향성 2-opt)는 유지했다. 최적화 버튼이나 유료/무료 구분은 추가하지 않았다. 현재 수정은 로컬 소스이며 서버 배포·APK 교체는 하지 않았다.

## 백엔드

- 사용자·지도 업무 범위·차량/도보·공급자 키 해시별로 독립된 이동시간 스냅샷을 사용한다. 좌표의 방향이 키이므로 A→B와 B→A가 다르다. 같은 좌표의 여러 업무는 구간만 공유하며 업무 ID/마커 번호는 합치지 않는다.
- 방문지 목록 전체가 캐시 키였던 차량 행 캐시를 제거했다. 새 목록의 필수 구간을 기존 스냅샷과 비교하고 빠진 것만 조회한다. 현재 위치로 되돌아가는 불필요한 구간 및 근무지에서 다시 출발하는 구간은 수집하지 않는다.
- 차량은 다중 목적지 행과 다중 출발지 열 중 많은 미조회 구간을 채우는 요청을 선택한다. 유효한 행렬에 한 곳을 추가하면 기본 2회다. 다중 출발지가 403/404/405로 허용되지 않으면 해당 미조회 구간만 다중 목적지로 채우고 이후 열 조회를 피한다. 이 경우 요청 수는 기본값보다 늘 수 있다.
- 도보는 최대 6개 연속 구간으로 묶어 구간별 시간을 저장한다. 전체 방향 행렬을 확보하므로 기존 8곳 초과의 일부 추정 구간 방식과 정보량이 다르다. 같은 시작/끝으로 인한 탐색 실패를 피하도록 요청 경계를 나눈다. 단계별 시간·구간 수·총합을 검증한 값만 저장한다.
- 1곳 이하에는 추천용 API를 쓰지 않는다. 상세 경로/실제 길안내는 별도다.
- 활성 업무의 구간에 300초 TTL을 적용하지 않는다. 자정이나 앱 재실행도 자동 API 호출을 일으키지 않는다. 구간과 수집 시각을 DB에 저장해 서버 재시작 뒤에도 불러온다.
- 다른 날 첫 차량 안내시작에서 전날 이전의 구간을 갱신한다. 당일 이미 수집한 값은 보존하고 그날 반복 안내시작은 전체 갱신하지 않는다. 등록만 계속하는 동안은 날짜가 달라도 갱신하지 않는다. 구형 프론트(안내시작 필드 없음)는 하루 첫 추천을 갱신 시점으로 삼아 무기한 오래된 차량 값이 쓰이지 않게 했다.
- 현재 위치가 실제로 이동했을 때는 출발 행만 채운다. 차량 30m/도보 10m 미만의 위치 흔들림은 이전 추천 출발점을 재사용한다. 실제 SDK/도보 상세 안내의 출발 위치를 바꾸는 규칙은 아니다.
- 같은 스냅샷의 동시 변경을 직렬화해 같은 구간을 중복 조회하지 않는다. 요청마다 동시에 대기시키는 배치도 4개로 제한한다. 이미 보낸 정상 배치는 다른 배치가 실패해도 저장하고, 실패 뒤 미전송 배치를 추가로 보내지 않는다. 실패한 구간은 캐시하지 않는다.

## 보관량과 개인정보

- 메모리 상한 128개 스냅샷, 스냅샷당 2,048구간. DB는 사용자당 최근 사용 16개 스냅샷으로 제한한다. 현재 계산에 필요한 구간을 우선 유지하고 완료 지점/과거 출발점 구간을 용량 초과 시 먼저 제거한다.
- 완료 취소나 다른 출발점 선택에 대비해 여유 공간의 구간은 재사용한다. 완료 지점으로 들어가는 구간은 새 추천에서 사용하지 않으며, 완료 장소가 현재 출발점이면 그곳에서 나가는 값은 사용할 수 있다.
- 조회만 한 캐시 적중에서는 전체 JSON을 다시 쓰지 않고 마지막 사용 시각만 갱신한다. 새 구간/출발점/신선도 상태가 바뀔 때만 스냅샷을 저장한다.
- 저장값에는 이동시간·좌표·수집 시각만 있고 API 키 원문·사진·전체 경로 선은 없다. 계정 탈퇴 시 해당 사용자의 DB/메모리 캐시를 제거한다.
- 며칠간의 사용 허용 기간에 대한 공급자 정책/계약은 별도 확인 항목이다. 차량 24시간·도보 7일이라는 임의의 장기 TTL은 확정 정책으로 추가하지 않았다.
- 다중 서버에서는 인스턴스별 동시 요청 합치기가 별개이므로 전역 중복 방지는 공용 잠금/캐시를 추가로 검토해야 한다. 이번 구현은 단일 서버의 메모리와 공용 DB 복원 기준이다.

## 프론트: 화면·입력 흐름 유지

- `MapScreen.js`에서 업무 범위와 실제 안내시작 이벤트를 서버로 전달한다. 날짜가 바뀌었다는 이유만으로 안내 중인 목적지를 바꾸지 않는다.
- 완료/삭제만 발생했다면 서버에 재추천을 요청하지 않고 현재 순서에서 번호만 당긴다. 완료 취소·새 방문지·좌표 변경에는 재추천한다.
- 새 추천을 기다릴 때 기존 순서를 유지하고 새 방문지를 임시로 뒤에 놓는다. 유효한 도로 시간 결과가 왔을 때만 결과를 반영해 거리 순서→도로 순서의 반복 깜빡임을 줄였다. 실패/지연 때 기존 목록을 유지한다.
- 200ms 내 연속 변경을 합치며 이전 요청을 취소하고 오래된 응답은 반영하지 않는다. 등록 저장 자체는 이 추천 완료를 기다리지 않는다.
- 안내 중/사용자가 먼저 선택한 방문지는 첫 목적지로 고정한다. 이동수단을 바꾸면 해당 모드로 나머지 순서를 다시 구하되 저장된 구간은 재사용한다.

## 검증

실제 카카오 호출 없이 MockRestServiceServer와 H2로 검증했다. 호출 수는 실제 청구/쿼터 계정 통계가 아닌 모의 요청 횟수다.

|순차 등록|차량 신규 HTTP|도보 신규 HTTP|
|---:|---:|---:|
|5곳|9회|7회|
|10곳|19회|22회|
|20곳|39회|77회|

- 601초 대기·등록 중 날짜 변경 후에도 기존 구간 재사용.
- 현재 위치만 변경했을 때 차량 출발 행 1회만 추가.
- 먼저 갈 방문지 변경, 완료/삭제 및 완료 취소의 기존 구간 재사용.
- 모드/사용자/업무 범위 분리, 동일 좌표 다중 업무 유지.
- 여러 동시 추천의 중복 조회 방지, 불완전 응답 미저장 및 실패 구간만 재시도.
- 새 서비스 인스턴스로 DB 스냅샷 복원, 실제 H2 저장/계정별 삭제.
- 백엔드 전체 108건: 실패 0, 기존 조건부 스킵 1. 이후 실패 배치 보존/캐시 정리 최종 변경의 관련 테스트 18건도 통과.
- 프론트의 순서·완료/취소·현재 위치 변경 판단·목적지 고정 단위 테스트와 MapScreen Babel 컴파일 확인.
- `recommendation-map-flow-test.cjs`는 실제 MapScreen 훅/이벤트를 제어해 연속 등록 합치기, 완료/삭제 무호출, 완료 취소, GPS만 변할 때 무호출, 오래된 응답 차단, 안내 목적지 고정을 검증한다. 기존 종합 화면 테스트는 과거 프로젝트 import/마커 동작용 mock이어서 수정하지 않고, 현재 추천 흐름용 독립 harness를 추가했다.

Windows PowerShell 재현 명령(임시 manifest 클래스패스의 리소스 누락을 피함):

```powershell
cd C:/PANG3-app/backend
mvn -o '-Dsurefire.useManifestOnlyJar=false' test
```

새 `visit_duration_snapshot` 테이블은 Hibernate `ddl-auto=update` 환경에서 생성된다. 수동 스키마 운영 환경용 SQL은 `backend/sql/visit_duration_cache.sql`에 있다. 기존 업무·보고서 테이블을 변경하지 않는다.
