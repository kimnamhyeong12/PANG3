# 자동추천 구간 재사용의 API 비용과 서버 부담

2026-10-26. 운영 코드 변경 없이 현재 소스 및 저장된 사하구 관측값으로 계산했다. 계정 청구 실측이 아닌 조건별 추정이다.

## 전제

- 빈 목록에서 방문지를 하나씩 추가한다. 등록 때마다 추천을 요청하되 각 요청은 이전 요청이 끝난 뒤 실행한다. 현재 위치는 고정, 근무지 복귀 없음, 좌표 중복 없음, 캐시는 등록 기간 동안 유효, API 실패/재시도 없음.
- 상세 경로 미리보기/안내, 지도 표시, 검색, 서버 기본요금은 제외한 **추천용 API만** 비교한다. 최초 일괄 등록과 순차 등록의 호출 수는 다르다.
- 차량 현재 코드는 방문지 목록을 캐시 키에 포함하므로 추가할 때마다 n+1개 출발행을 재조회한다. 1곳 때도 현재 코드는 2회를 호출한다. 수정안은 1곳의 추천용 조회를 생략한다.
- 도보 현재 코드는 이미 구간별 캐시가 있다. 따라서 5곳의 현재 누적 호출을 1²+2²+…+5²=55회로 계산하면 안 된다. 동일 구간은 재사용되므로 이번 조건에서는 25회다.

## 공식 가격 및 무료 제공량

- 차량 다중 목적지: 초과 요청당 20원(게시된 월 유료 30만 건 이하 구간). 다중 출발지/목적지의 일일 제공량은 각각 1,000건. **다중 출발지 초과 단가는 공식 공개 가격표에 없어 확정 금액을 만들지 않았다.**
- 도보 경로 조회: 초과 요청당 10원, 일일 제공량 1,000건. 카카오맵 무료 쿼터는 개발자 계정의 첫 활성 앱에만 제공된다는 조건이 있다.
- 실제 청구는 무료 잔여량, 유료 이용 설정, 계약 단가, 계정 통계에 따라 달라진다. 아래 도보 묶음 추정은 HTTP 요청 1개가 과금/쿼터 1건이라는 전제이며 콘솔 대조 전 확정 청구액으로 해석하지 않는다.

## 차량: 순차 등록 1세트

기존 호출은 N(N+3)/2회. 수정안은 2곳에서 초기 필요한 구간을 3회로 채운 뒤 추가마다 2회여서 다중 목적지 N회 + 다중 출발지 N-1회다. 이는 검증된 API 구성에 기초한 설계 계산이며 수정 코드 실호출 결과는 아니다.

|최종 방문지|현재 호출|수정안 호출|요청 수 감소|모든 요청이 유료일 때 현재 금액|수정안 금액|
|---:|---:|---:|---:|---:|---|
|5|20|9 (목적지 5 + 출발지 4)|55.0%|400원|100원 + 출발지 4회 단가|
|20|230|39 (목적지 20 + 출발지 19)|83.0%|4,600원|400원 + 출발지 19회 단가|
|29|464|57 (목적지 29 + 출발지 28)|87.7%|9,280원|580원 + 출발지 28회 단가|

예를 들어 다중 출발지 단가도 **가정상** 20원이라면 수정안은 180/780/1,140원이 된다. 20원이 공식 출발지 단가라는 뜻은 아니다.

## 도보: 순차 등록 1세트

현재 로직을 추출한 Java solve 메서드와 기존 최근접 후보/2회 경로 보완 과정을 사용해 저장된 20곳의 실제 도보 행렬을 오프라인 재생했다. 현재 캐시가 계속 유효하다고 보고 새 구간 호출만 셌다. 통신 지연, 25초 제한, 전역 요청 보호 한도는 제외했으므로 실제 앱 세션의 확정 호출 수는 아니다.

수정안은 새 구간들을 출발점→새 방문지→기존 방문지→새 방문지… 형태로 연결하고 6개 구간씩 분할한 계획이다. 2곳의 최초 수집은 두 요청을 사용한다. 반복 경유는 이전 소규모 실호출에서 확인했지만 이번 전체 순차 배치 계획을 실호출한 것은 아니다. 실패 분할 시 추가된다.

|최종 방문지|현재 누적 호출 (기록 재생)|수정안 누적 HTTP (배치 계획)|요청 수 감소|전부 유료일 때 현재|수정안 추정|
|---:|---:|---:|---:|---:|---:|
|5|25|7|72.0%|250원|70원|
|20|199|77|61.3%|1,990원|770원|

20곳 현재 방식은 8곳 초과부터 일부 후보와 경로만 조회한다. 수정안 77회는 전체 400개 방향 구간을 채우는 계획이므로 **조회 정보량까지 동일한 비교는 아니다**. 앞서 검증된 72회는 20곳을 처음부터 한꺼번에 채우는 별도 수집 사례이며, 하나씩 등록하는 이 계획의 77회와 혼동하지 않는다. 도보는 현재 추천 상한이 20곳이므로 29곳 금액을 제시하지 않는다.

## 하루 10명이 각각 20곳씩 순차 등록, 월 22일 예시

다른 사용량 없이 각 API의 무료 제공량이 온전히 남아 있고, 사용자별 구간이 달라 사용자 사이 추가 재사용은 없다고 가정한다. 매일 새로운 유효 캐시 기간에 처음 수집한다.

|사용 패턴|현재 추천 비용/월|수정안 추천 비용/월|
|---|---:|---:|
|차량만 사용|572,000원|0원 (목적지 200회/일, 출발지 190회/일)|
|도보만 사용|217,800원|0원 추정 (770회/일)|

차량 현재: (230×10-1000)×20×22=572,000원. 도보 현재: (199×10-1000)×10×22=217,800원. 도보 수정안의 0원은 위 배치 성공·쿼터 집계 전제에 따른 추정이다. 무료 한도 내여도 사용량 제한/권한 설정 때문에 무조건 서비스 이용이 보장되는 것은 아니다.

이 조건에서 차량 순차 등록 1세트/인/일의 무료 처리 인원은 5곳 50→200명, 20곳 4→50명, 29곳 2→34명이다. 상세 경로/다른 추천 세션/위치 이동/캐시 만료가 추가되면 달라진다.

## 재사용이 서버에 주는 부담

- 저장값은 이동 모드, 출발/도착 좌표 식별자, 옵션, 예상 소요 초, 수집 시각이다. A→B와 B→A를 따로 보관하고 차량/도보도 분리한다. 추천 캐시에는 전체 선 좌표나 안내 단계가 필요 없다.
- 복귀 없는 N곳 추천에 필요한 방향별 시간은 N²개다. 20곳 400개, 29곳 841개다. 29곳의 시간 숫자만 double로 저장하면 6,728 bytes(약 6.6KiB). 1,000개 독립 세트는 숫자만 약 6.4MiB지만, 키/객체/좌표/시각과 자료구조가 추가되므로 이를 실제 JVM 사용량이라고 주장하지 않는다.
- 현재도 인메모리 캐시를 사용한다. 차량은 행 캐시 최대 256개, 도보는 구간 캐시 최대 4,096개이며 유효기간은 모두 5분이다. 수정안도 먼저 프로세스 내부의 크기 제한 캐시를 사용하면 추가 서버나 유료 캐시 상품을 필수로 도입할 필요가 없다.
- 구간별 최대 개수와 메모리 예산을 두고 오래되거나 사용이 뜸한 항목부터 제거한다. 만료되었다고 즉시 모두 재조회하지 않고, 실제 요청에서 필요한 것만 갱신한다. 메모리 상한 때문에 제거된 구간은 다음 사용 시 다시 조회할 수 있다.
- 대기 중인 같은 구간 요청도 합쳐 중복 통신을 줄인다. 조회는 빠르지만 자료구조 관리와 GC 비용은 추가된다. 실제 heap/RSS·캐시 적중률·새 API 요청 수로 구현 후 측정해야 한다.
- 방문지 변경 시에도 순서 계산 자체는 필요하다. 재사용이 순서 계산 CPU를 없애는 것은 아니다. 주로 카카오 통신/대기/응답 파싱을 줄인다. 1대 서버가 재시작되면 메모리 캐시는 비워지고, 여러 인스턴스로 확장하면 로컬 캐시끼리 자동 공유되지 않는다. 그 시점에만 공용 저장소를 검토한다.
