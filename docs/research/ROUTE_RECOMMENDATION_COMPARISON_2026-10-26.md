# 자동 방문 순서 추천: 기존 방식과 절약 후보 방식 실측 비교

실행일: 2026-10-26. 운영 앱과 서버의 추천 로직은 수정하지 않았다.

## 조건

- 카카오 장소 검색으로 사하구의 공원 관련 실제 장소 20곳을 선택했다. 출발지는 다대포 인근 고정 좌표다.
- 장소를 넓게 분산시키는 결정적 선택 규칙을 사용했다. 5곳은 선택 순서의 첫 5곳, 20곳은 전체다. 5곳도 사하구 안에서 넓게 분산된 표본이며 일반적인 짧은 도보 업무를 대표하지 않는다.
- 각 비교는 캐시 없는 최초 추천 1회를 가정했다. 하나씩 등록하며 발생하는 누적 호출 비교가 아니다.
- 근무지 복귀, 첫 목적지 지정, 작업 완료, 출발지 이동은 제외했다.
- 같은 방향의 같은 구간은 같은 카카오 응답 값을 사용해 교통 변화에 따른 차이를 배제했다. 호출 수는 각 알고리즘이 독립적으로 필요로 한 요청 수다.
- 시간은 카카오가 반환한 구간별 예상 이동시간의 합계이며 실제 주행/보행 실측이나 현장 작업시간이 아니다.
- 호출 수는 HTTP 요청 수이며 계정 청구서의 과금 건수나 실제 청구액을 검증한 결과는 아니다.

## 비교한 방식

### 기존

현재 `VisitOrderService.java`의 TSP/근사 풀이를 그대로 사용했다.

- 차량: 출발지 및 각 방문지에서 다른 지점들까지 다중 목적지 API로 조회한 뒤 순서를 계산한다.
- 도보 5곳: 모든 방문지 방향 구간을 조회한다. 출발지로 돌아오는 구간은 조회하지 않는다.
- 도보 20곳: 각 출발점의 가까운 후보 4곳을 조회하고, 나머지는 거리로 추정한다. 계산한 경로를 실제 시간으로 확인하고 한 차례 다시 계산/확인한다. 기존 방식 자체도 근사치다.

### 절약 후보 시제품

- 거리 행렬에 현재 서버의 TSP/근사 풀이를 적용해 기본 순서를 생성한다.
- 차량: 각 출발점에서 기본 순서의 다음 목적지와 가까운 후보 2곳을 묶어서 조회한다고 가정한다. 확인한 구간만으로 구성할 수 있는 순서 중에서 재배치/구간 뒤집기로 개선한다. 다중 목적지 API이므로 HTTP 요청 수는 기존과 같다.
- 도보: 기본 경로의 실제 이동시간을 먼저 조회한다. 확인된 구간의 초당 거리 비율로 미조회 구간을 추정해 유리해 보이는 재배치/구간 뒤집기를 검사한다. 추가 후보 조회를 포함해 최대 `방문지 수 × 2`건으로 제한한다. 확정 순서는 실제로 조회한 구간만으로 구성한다.
- 개선 가능성이 없다고 판단하면 예산을 모두 쓰지 않고 종료한다. 예산은 최대치이지 고정 호출 횟수가 아니다.
- 모든 구간을 비교한 전체 최적 순서를 보장하지 않는다. 현재 운영에 적용되지 않은 비교 시제품이다.

## 결과

| 방문지 | 모드 | 기존 호출 | 후보 호출 | 기존 예상 이동시간 | 후보 예상 이동시간 | 이동시간 변화 |
|---|---|---:|---:|---|---|---:|
| 5곳 | 차량 | 6 | 6 | 52분 14초 | 52분 14초 | 0% |
| 5곳 | 도보 | 25 | 5 | 5시간 41분 32초 | 5시간 45분 15초 | +1.09% / 3분 43초 증가 |
| 20곳 | 차량 | 21 | 21 | 2시간 12분 39초 | 2시간 17분 28초 | +3.63% / 4분 49초 증가 |
| 20곳 | 도보 | 103 | 35 | 16시간 26분 21초 | 13시간 41분 34초 | -16.71% / 2시간 44분 47초 감소 |

도보 호출 감소: 5곳은 80%, 20곳은 약 66.02%.

## 해석

- 5곳 도보에서는 호출이 줄어든 대가로 이동시간이 조금 늘었다. 품질 손실이 발생할 수 있다는 실제 사례다.
- 20곳 도보에서는 기존의 일부 구간 추정 방식보다 시제품이 더 좋은 경로를 찾았다. 기존 방식도 최적해가 아니므로 가능한 결과다. 이 한 사례로 시제품이 일반적으로 더 정확하다고 결론낼 수 없다.
- 차량은 후보 목적지 수를 줄여도 다중 목적지 HTTP 요청 수가 줄지 않았다. 20곳에서는 이동시간만 늘었다. 차량에 이 후보 축소 방식을 적용할 근거가 되지 않는다. 차량은 조회 정보 축소보다 구간별 캐시/변경 구간 재사용/완료 후 불필요한 재조회 방지가 우선이다.
- 한 출발지와 한 장소 집합의 비교다. 평균, 최악의 품질 손실, 실제 교통 반영 정확도, 여러 사용자 동시 부하는 아직 검증하지 않았다.

## 검증 및 재현

비교 스크립트는 현재 서버 소스에서 `solve`/`cost` 메서드를 추출해 Java로 실행한다. 기존 결과는 별도로 **현재 `VisitOrderService` 전체를 실제로 호출**하고, 기록한 카카오 응답을 HTTP 모의 응답으로 넣어 순서·요청 수·총 이동시간을 재검증했다. 네 가지 경우 모두 일치했다.

- `tools/compare-route-recommendations.py`: 수집과 두 알고리즘 비교. 기본 실행은 저장된 관측값만 사용한다. 새 실제 조회에는 `--live`가 필요하다.
- `tools/RouteComparisonReplay.java`: 운영 서비스 코드에 관측 응답을 넣는 오프라인 검증.
- `tmp/route-comparison/observations.json`: 실제 장소와 구간별 관측값. API 키는 저장하지 않았다.
- `tmp/route-comparison/results.json`: 결과, 순서, 현재 소스 해시.

실제 신규 요청 합계는 장소 검색 3회, 차량 다중 목적지 21회, 도보 132회였다. 두 방식이 관측 응답을 공유하므로 표의 논리적 호출 수를 단순 합한 것과 다르다. 차량은 비교/평가용 전체 행렬을 한 번 수집하되, 절약 후보 알고리즘에는 정해진 후보 구간만 노출했다.

수집은 영구 비교 파일을 만들기 위해 순차 실행했고, 비교 계산은 저장된 같은 관측값으로 재생했다. 운영의 25초 제한, 5분 캐시 만료, 네트워크 실패에 의한 거리 기준 폴백, 동시 요청의 효과까지 비교한 부하 테스트는 아니다. 제한 오류를 숨겨서 실제 이동시간으로 취급하지 않았다.

실행 예:

```powershell
python tools/compare-route-recommendations.py

cd backend
mvn -o dependency:build-classpath '-Dmdep.outputFile=target/route-comparison-classpath.txt' '-Dmdep.includeScope=test' -q
cd ..
$taskRouteCp = (Get-Content backend/target/route-comparison-classpath.txt -Raw).Trim() + ';C:\PANG3-app\backend\target\classes'
javac -encoding UTF-8 -cp $taskRouteCp -d tmp/route-comparison tools/RouteComparisonReplay.java backend/src/main/java/com/fieldwork/service/VisitOrderService.java
java -cp ('C:\PANG3-app\tmp\route-comparison;' + $taskRouteCp) RouteComparisonReplay C:\PANG3-app\tmp\route-comparison
```
