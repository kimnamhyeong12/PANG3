# 자동 방문 순서 추천 최종 설계안

작성일: 2026-10-26. 논문·공식 API 문서 조사와 제한된 실제 API 검증에 기반한 구현 설계다. 운영 추천 로직은 아직 수정하지 않았다.

후속 검증 업데이트: [알고리즘 실제 비교 보고서](ROUTE_ALGORITHM_BENCHMARK_2026-10-26.md)에서 도보 20곳의 전체 400구간을 묶음 **72회 실호출로 확보**했고 기존 132개 구간과 모두 일치했다. 따라서 아래의 ‘72회 전체 실호출 전’이라는 문구는 최초 설계 당시의 상태이며 후속 보고서가 최신이다. 같은 전체 행렬로 11개 계산 구성을 비교했고 정확 DP와 CP-SAT가 최적값을 확인했다. CP-SAT도 운영 후보로 추가 검토해야 하므로 ‘13곳 이상은 GLS만’이라는 초기 선정은 최종 배포 결론으로 사용하지 않는다.

## 1. 결정

자동 추천과 차량/도보 선택 UI는 유지한다. 별도의 경로 최적화 버튼을 추가하지 않는다.

**우선안은 실제 이동시간 정보를 줄이지 않고 묶음 조회·증분 갱신·구간 재사용으로 호출을 줄이는 것이다.** 앞서 시험한 ‘거리로 후보를 좁히고 일부만 조회’ 방식은 기본안에서 뒤로 미룬다. 실제 시간이 충분하지 않거나 요청 예산이 부족할 때의 제한된 보조 전략으로 사용한다.

방문 순서 문제는 방향별 이동시간이 다른 동적 단일 작업자 TSP 경로 문제로 모델링한다. 출발점은 현재 위치이며, 근무지 복귀가 없으면 열린 경로, 있으면 지정된 근무지가 고정 종점이다. 먼저 가기로 선택한 목적지와 안내 중 목적지는 제약으로 고정한다. 팀 전체의 업무 배분/다중 차량 배차까지 이 변경에 포함하지 않는다.

순서 계산기는 12곳 이하에 기존 Held–Karp 동적 계획법을 개선해 유지하고, 13~29곳은 OR-Tools Java Routing의 초기 순서 재사용 + Guided Local Search를 채택한다. 모든 구간이 실제 값이어야 작은 문제의 실제 시간 기준 최적성을 주장할 수 있다. OR-Tools의 일반 Routing 결과는 전역 최적해라고 표시하지 않는다.

## 2. 조사한 알고리즘 계열과 선정 이유

| 계열 | 우리 앱에서의 역할과 판단 |
|---|---|
| Dijkstra / A* / 도로 그래프 전처리 | 도로 위 두 지점 사이 경로를 구하는 계열이다. 현재는 카카오가 해당 역할을 맡는다. 자체 도로망을 운영하지 않는 조건에서 방문 순서 계산기의 대체재로 사용할 수 없다. |
| 최근접 이웃 / Cheapest Insertion / Regret Insertion | 빠른 초기 순서, 기존 순서에 새 방문지 삽입용으로 적합하다. 단독으로 최종 추천 품질을 보장하지 않는다. |
| Held–Karp DP | 작은 방향성 행렬의 최적 순서를 구하는 데 적합하다. 지수적으로 커지므로 운영의 모든 20~29곳 요청에 무조건 적용하지 않는다. 12곳을 초기 경계로 유지하고 서버 자원 측정 후 조정한다. |
| Relocate / Swap / Or-opt / 방향성을 고려한 2-opt | 방문지 이동·교환 등으로 현재 순서를 개선한다. A→B와 B→A를 같다고 가정하는 단순 뒤집기 비용식을 쓰지 않는다. OR-Tools의 방향별 비용 평가를 사용한다. |
| Guided Local Search / Tabu / Simulated Annealing | 한 가지 순서 주변에서 개선이 멈추는 현상을 벗어나기 위한 탐색 전략이다. OR-Tools가 제공하는 GLS를 기본으로 선정한다. |
| LKH / LKH-3 | 강력한 비교 후보지만 실제 구간 정보 부족을 해결해주지는 않는다. 네이티브 통합과 상업 이용 조건도 고려해야 한다. 우리 규모와 Java 서비스에는 OR-Tools를 우선한다. LKH-3 기술 보고서는 학술·비상업 이용 조건을 명시한다. |
| MIP / CP-SAT / Branch-and-cut | 오프라인 품질 기준을 만들 때 사용한다. 최적성 증명이 끝난 표본만 최적 기준으로 취급하고, 시간 제한으로 끝났으면 발견한 최선의 해와 하한을 함께 기록한다. |
| Christofides 등 대칭 거리 기반 근사 | 방향별 비용이 다른 도로 시간 행렬에 대칭 거리 문제의 근사 보장을 그대로 적용할 수 없다. 기본 계산기로 선택하지 않는다. |
| 유전·군집·신경망 / 강화학습 TSP | 계산 방법의 후보이지만 관측하지 않은 실제 도로 시간을 만들어주지는 않는다. 학습/분포 검증 부담을 추가하는 것보다 현재 규모에서는 검증된 계산기를 우선한다. |
| Lazy edge evaluation | API 호출이 비싼 상황에서 조회 대상을 늦게 고르는 아이디어로 참고한다. LazySP는 단일 최단 경로 연구이며, 이를 우리 TSP에 적용한다고 그 논문의 최적성 보장이 자동으로 따라오는 것은 아니다. |

근거:

- [Dijkstra, 1959](https://link.springer.com/article/10.1007/BF01386390): 도로 그래프의 최단 경로 문제와 여러 방문지 순서 문제를 구분하는 기반.
- [Held & Karp, 1962](https://epubs.siam.org/doi/abs/10.1137/0110015): 작은 순서 문제에 대한 동적 계획법 원전. 본문은 유료 접근이므로 서지와 현재 구현의 DP 구조를 함께 확인했다.
- [OR-Tools Routing Options](https://developers.google.com/optimization/routing/routing_options): 초기해 전략, GLS·Tabu·SA, 탐색 시간 제한.
- [OR-Tools TSP](https://developers.google.com/optimization/routing/tsp): 행렬을 이용한 계산과 일반 Routing의 최적해 비보장.
- [Helsgaun, LKH-3 technical report, 2017](https://forskning.ruc.dk/en/publications/an-extension-of-the-lin-kernighan-helsgaun-tsp-solver-for-constra/): 제약이 있는 순서/차량 경로 문제와 이용 조건. 대학 연구 포털의 초록·이용 조건을 확인했다.
- [Heins 외, PPSN 2024](https://arxiv.org/abs/2407.03927): 후보 집합 구성에 따라 탐색 성능이 달라짐. 가까운 후보 몇 개만 고정하는 것이 일반적인 품질 보장은 아니라는 판단에 참고했다.
- [Dellin & Srinivasa, ICAPS 2016](https://www.ri.cmu.edu/pub_files/2016/3/paper-lazysp.pdf): 구간 비용 평가가 비싼 경우의 지연 평가.
- [POMO, NeurIPS 2020](https://arxiv.org/abs/2010.16011): 학습 기반 조합 최적화 후보. 논문의 벤치마크 수치를 우리 도로 시간 행렬의 정확도로 옮겨 쓰지 않는다.
- [GOAL, ICLR 2025](https://proceedings.iclr.cc/paper_files/paper/2025/file/826aea2253363fe04e8c4991b2a8869e-Paper-Conference.pdf): 좌표만의 문제와 비용 행렬 문제를 구분하는 최근 학습 접근도 검토했다. 이 앱에 바로 투입할 검증된 모델이라는 근거는 없다.
- [동적 차량 경로 문제 검토 보고서](https://www.cirrelt.ca/documentstravail/cirrelt-2011-62.pdf): 신규 작업과 진행 중 경로가 바뀌는 문제의 배경 자료.

세계의 모든 변형 알고리즘을 전수 확인했다는 의미는 아니다. 우리 문제와 관련 있는 주요 계열을 비교해 운영 적용안을 선정했다. OR-Tools가 모든 표본에서 LKH보다 우수하다고 입증한 것도 아니다.

## 3. 이번 조사에서 확인한 API 절감 수단

### 차량: 행 조회와 열 조회를 함께 사용

현재 코드는 다중 목적지 API만 사용한다. 공식 API에는 다중 출발지도 있다.

- [다중 목적지](https://developers.kakaomobility.com/guide/navi-api/destinations.html): 한 출발지에서 최대 30개 목적지.
- [다중 출발지](https://developers.kakaomobility.com/guide/navi-api/origins.html): 최대 30개 출발지에서 한 목적지.

기존 행렬이 유효할 때 새 방문지 X를 추가하면:

1. 기존 출발점·방문지들 → X를 다중 출발지 1회로 채운다.
2. X → 기존 남은 방문지들·선택적 근무지를 다중 목적지 1회로 채운다.
3. 기존 행렬과 합쳐 순서를 다시 계산한다.

**행렬이 유효하고 API 범위 안이라는 조건에서 새 방문지 1개에 HTTP 2회로 모든 새 방향 구간을 채울 수 있다.** 현재 위치 행이 따로 바뀌었거나 캐시가 만료되었다면 그 조회는 추가된다. 다중 출발지와 다중 목적지는 종류별 쿼터를 따로 계수한다. 출발지/목적지 수 및 반경 제한은 계획 단계에서 확인한다.

실제 앱 키로 다중 출발지 1회를 호출했고 세 출발지의 결과가 모두 성공했다. 행/열 API 간 시간 기준과 출입점 매칭, 실제 쿼터 차감·요금은 운영 계정에서 추가 확인할 계약 테스트 항목이다.

### 도보: 경유지 묶음으로 실제 구간 정보를 보존

[카카오맵 REST 문서](https://developers.kakao.com/docs/ko/kakaomap/rest-api)에 따르면 도보도 `via_x`/`via_y` 최대 5개를 받는다. 최대 7개 지점을 연결한 **6개 연속 구간**을 한 요청으로 조회할 수 있고, `legs[].properties.time`에 각 구간 시간이 있다.

현재 `KakaoWalkingClient`는 경유지를 전달하지 않고 전체 경로를 한 덩어리로 정규화하므로 이 이점을 사용하지 못한다.

새 클라이언트는 요청 지점 순서와 응답 leg를 대응시켜 구간별 시간·거리·출처·시각을 분리해 저장한다. 구간 수, 상태, 시간 합계, 좌표 대응을 검증한다. 같은 도보 옵션을 사용해야 하며, 현재 `BROAD_FIRST`(넓은 길 우선)를 그대로 유지한다. 최단 거리 옵션으로 조용히 변경하지 않는다.

새 구간 조회를 6개 이하의 연속 요청으로 묶는다. 이는 순서를 카카오에 최적화해달라는 요청이 아니라 **우리가 지정한 구간들의 실제 시간을 한꺼번에 얻는 수집 수단**이다.

실제 검증 결과:

| 검증 | 결과 |
|---|---|
| 5개 구간 경로 1회 | 응답 5 legs, 개별 조회 시간과 모두 일치 |
| 6개 구간 경로 1회 | 응답 6 legs, 개별 조회 시간과 모두 일치 |
| 5곳 전체 방향 구간 25개 | 묶음 6회로 수집, 기존 개별 조회 25개 값과 모두 일치 |
| 같은 방문지가 반복되는 경유 경로 2회 | 두 요청 모두 성공, 각 5개 leg 시간이 기존 값과 모두 일치 |

추가 오프라인 재생에서 새 묶음 응답만으로 5곳 전체 행렬을 구성하고 현재 정확 DP를 돌렸다. 기존과 동일한 순서, 동일한 20,492초(5시간 41분 32초)를 얻었다. 이 표본에서는 25→6회로 줄이면서 추천 결과도 그대로 유지했다.

이 검증에 사용한 실제 신규 호출은 도보 총 10회, 차량 다중 출발지 1회다. 본 연구 중 새로 20곳 전체를 조회하지 않았다.

5곳의 전체 행렬 묶음 수집은 정보를 덜 쓰지 않으면서 호출을 줄인 실제 사례다. 모든 지역·모든 경유 조합이 독립 구간 조회와 항상 같다고 증명한 것은 아니다. 20곳과 다른 지역 표본에서 교차 검증을 진행한 뒤 채택한다.

## 4. 행렬을 보존하는 기본 수집 정책

### 최초 목록

- 0~1곳은 순서를 비교할 필요가 없으므로 추천용 조회를 생략한다. 사용자가 상세 경로를 볼 때 필요한 조회는 별도다.
- 차량 2~29곳: 필요한 방향별 실제 시간 행렬을 묶음으로 확보한다. 이미 있는 구간은 조회하지 않는다.
- 도보 2~20곳: 가능한 요청 예산 안에서는 전체 실제 시간 행렬을 경유지 묶음으로 확보한다. 거리 추정치를 실제 시간인 것처럼 섞지 않는다.
- 중간 상태의 즉시 화면 표시에는 거리 기반 순서를 사용할 수 있다. 실제 시간이 확인되면 현재 조건에 해당하는 결과를 한 번 반영한다. 안내 중 목적지는 고정한다.

### 기존 목록 변경

- 추가: 기존 행렬을 유지하고 새 지점 관련 행/열만 채운다.
- 삭제: 기존 행렬의 부분집합을 사용한다. 현재 위치나 만료로 부족해진 구간이 없다면 조회하지 않는다.
- 완료: 추천대로 현재 방문지를 완료했다면 남은 순서를 유지하고 번호만 당긴다.
- 우선 목적지 변경: 그 목적지를 고정하고 저장한 행렬로 남은 순서를 다시 푼다. 구간이 부족하거나 오래되었을 때만 추가 조회한다.

기존 시간 행렬을 가지고 추가·삭제·우선 방문 변경 후 전체 남은 순서를 **서버 CPU로 다시 계산하는 것 자체는 API 비용을 늘리지 않는다.** 단순 삽입은 초기 후보 생성에 활용하고, 정보가 충분한데도 최종 결과를 삽입만으로 제한하지 않는다.

### 호출 수의 의미

근무지 복귀 없는 콜드 추천 1회에 대한 비교다. 최초 수집과 등록 누적을 혼동하지 않는다.

| 경우 | 기존 | 새 수집 방식 | 근거 수준 |
|---|---:|---:|---|
| 차량 5곳 최초 전체 행렬 | 6회 | 6회 | 묶음 목적지 특성상 최초 횟수 동일 |
| 차량 20곳 최초 전체 행렬 | 21회 | 21회 | 동일 |
| 차량 새 방문지 1개 추가 | 기존은 행 목록 변경으로 재조회 | 기본 2회 | 유효한 기존 행렬, 동일 출발점/옵션/반경을 가정한 설계 계산 |
| 도보 5곳 최초 전체 행렬 | 25회 | 6회 | 실제 25개 값 전체 일치 검증 완료 |
| 도보 20곳 최초 | 이전 표본 103회, 일부 구간만 조회 | 전체 400개 방향 구간을 72개 묶음으로 구성 가능 | **오프라인 요청 배치 계획 검증만 완료. 72회 실호출 실험 전** |

도보 20곳의 72는 모든 경로에서 보장하는 고정값이 아니다. `tools/plan-walking-batches.py`가 400개 구간을 빠짐없이 한 번씩, 각 요청에 6개 이하로 넣고 요청 내 좌표 중복 없이 구성했을 때의 계획 결과다. 실제 장소 중복, 경유지 탐색 실패, 근무지 복귀, 캐시 상태에 따라 달라진다. 실패 분할과 추가 호출까지 요청 예산에 포함한다.

새 방문지 1개를 더하는 도보 구간은 왕복 방향을 번갈아 연결한 경유 요청으로 묶을 수 있다. 반복 경유는 작은 표본에서 확인했지만 모든 사례에 보장하지 않는다. 연결되지 않는 지점, 실패 응답, 같은 시작/끝 처리 등은 명시적인 계약 테스트와 제한된 분할 정책으로 다룬다.

위 숫자는 HTTP 요청 수다. 경유 요청의 실제 계정 쿼터 차감 방식과 다중 출발지 추가 요금은 콘솔/공급자 기준으로 확인하고 최종 비용 산식에 반영한다. 요청 감소를 확인한 것과 청구액 감소를 측정한 것은 구분한다.

## 5. 순서 계산기

### 12곳 이하

Held–Karp DP를 유지하되 열린 경로·고정 종점·고정 첫 목적지를 명시적으로 모델링한다. 행렬에 실제 값이 모두 있어야 해당 행렬의 최적해로 표시한다. 추정 행렬에서 계산한 최적해를 실제 도로의 최적해라고 표시하지 않는다.

### 13~29곳

OR-Tools Java Routing + Guided Local Search를 사용한다.

- 이전 순서, 거리 기반 순서, 삽입 기반 순서를 초기 후보로 준비한다.
- 현재 가장 좋은 유효 순서를 초기해로 주고, 정해진 계산 시간 안에서 개선한다.
- 방향별 초 단위 비용을 사용하고 목적지별 번호/업무 식별자와 분리한다.
- 현재 안내 목적지, 이미 완료한 구간, 근무지 종점 등 강제 조건을 먼저 적용한다.
- 계산기 비용 콜백에서는 API를 호출하지 않는다. 고정된 행렬 스냅샷만 읽는다.
- GLS 탐색용 벌점이 포함된 목적함수 값을 실제 이동시간으로 노출하지 않는다. 최종 순서를 원래 시간 행렬로 다시 합산한다.
- 작업을 자동 누락하는 disjunction/벌점 모델을 쓰지 않는다. 갈 수 없는 방문지는 목록에 남기고 별도로 설명한다.

[Java/Maven 지원](https://developers.google.com/optimization/install/java), [초기 순서/제한 시간](https://developers.google.com/optimization/routing/routing_tasks), [라이선스](https://github.com/google/or-tools/blob/stable/LICENSE)를 확인했다. 기존 Java 17/Debian 계열 컨테이너에서 네이티브 로더·메모리·동시 실행 테스트를 구현 단계의 필수 확인으로 둔다. 별도의 유료 최적화 서비스나 경로 엔진 서버는 추가하지 않는다.

CPU 초기 예산은 빠른 결과 수백 ms, 백그라운드 개선 최대 약 1초 수준을 시험 출발점으로 잡되, 실제 운영 서버 부하 측정 전 지연 시간을 보장하지 않는다. 탐색 스레드 수와 전체 작업 수를 제한한다.

## 6. 예산 부족/부분 행렬일 때의 보조 전략

모든 사용자가 무제한 자동 추천을 하면서 매번 전체 실제 행렬과 전역 최적성을 보장하고, 정해진 무료 쿼터도 지키는 것은 보장할 수 없다. 이를 숨기지 않고 안전한 축소 동작을 둔다.

1. 해당 방문지 집합의 저장된 유효 순서를 우선 보존한다.
2. 없으면 거리 순서/이전 순서/삽입 순서 등 서로 다른 후보를 만든다.
3. 후보 전체 경로를 실제 시간으로 확인할 예산을 먼저 확보한다.
4. 추가 후보는 가까운 지점뿐 아니라 실제 우회가 큰 구간, 서로 다른 초기해에서 공통으로 나타나는 구간, 조회 후 판단이 바뀔 여지가 큰 구간을 함께 고려한다.
5. 추정 개선량 대비 새 HTTP 요청 비용을 사용해 조회 우선순위를 정한다. 이 추정치는 통계적 신뢰구간이나 증명된 하한이라고 부르지 않는다.
6. 전체 시간이 실제로 확인된 후보만 현재 최선과 비교한다. 더 나쁜 결과로 덮어쓰지 않는다.
7. 한도가 끝나면 확인된 가장 좋은 순서를 반환한다. 기존 결과와도 조건이 달라 직접 비교할 수 없다면 품질을 확정한 것처럼 표시하지 않는다.

LazySP의 선별 평가 아이디어를 참고한 앱별 정책이며 전역 최적 보장은 없다. 데이터가 부족한데도 '정확도 95%' 같은 수치를 만들지 않는다. 일부만 실제 시간인 행렬을 하나의 `roadDuration` 상태로 뭉뚱그리지 않는다.

## 7. 사용자가 느끼는 동작

| 사건 | 동작 | 추천 API |
|---|---|---|
| 방문지 최초 등록 | 즉시 목록 표시, 두 곳 이상이면 자동 계산 | 없는 구간만 조회 |
| 엑셀/공공데이터/프로젝트 일괄 등록 | 일괄 추가 전체를 한 사건으로 처리 | 중간 개수마다 반복하지 않음 |
| 한 곳 추가 | 기존 결과를 유지하며 부족한 행/열 보완 후 갱신 | 증분 묶음 조회 |
| 마커를 눌러 카드 보기 | 해당 방문지 상세 경로 표시 | 상세 경로만 필요에 따라 조회; 순서를 바꾸지 않음 |
| 추천 첫 목적지로 안내 시작 | 확정 순서와 목적지 유지 | 시작 자체로 전체 재조회하지 않음 |
| 다른 방문지로 먼저 안내 | 선택 목적지를 첫 번째로 고정, 이후 순서 다시 계산 | 유효한 행렬이면 순서용 신규 조회 없음 |
| 추천대로 작업 완료 | 완료 항목 이동, 남은 순서 유지·번호 당김 | 순서용 조회 없음 |
| 차량↔도보 변경 | 해당 모드의 유효한 순서·행렬 우선 사용 | 유효하면 0, 최초/누락/만료 시 필요 부분 조회 |
| 메모·사진·업무유형 수정 | 추천 조건 불변 | 없음 |
| GPS 작은 흔들림 | 화면 위치만 갱신 | 전체 재조회 없음 |
| 출발지가 의미 있게 바뀜 | 현재 위치와 후보 첫 방문지 사이 연결 갱신 | 출발점 관련 구간만 조회 |
| 경로 이탈 | 현재 목적지까지 안내 경로 재탐색 | 남은 전체 순서는 유지 |
| 근무지 복귀 선택 변경 | 고정 종점 제약과 필요한 구간 갱신 | 필요한 종점 구간만 조회 |

‘의미 있는 위치 변화’의 거리 기준은 GPS 정확도·현재 안내 상태와 함께 정한다. 좌표를 거칠게 반올림해 큰길 반대편/육교 위아래를 같은 출발점으로 취급하지 않는다. 2초 디바운스로 20초 걸리는 개별 등록을 하나로 묶을 수 있다고 가정하지 않는다.

현재 `membershipKey`에 완료 상태가 포함되고 `isGuiding`/목적지 변화가 전체 추천 effect를 건드리는 구조를 사건별 정책으로 교체한다. 늦게 끝난 과거 계산이 최신 모드/방문지 목록/선택 목적지를 덮어쓰지 않도록 버전 번호를 검사한다.

## 8. 구간 저장, 상세 경로 재사용, 유효기간

구간 키는 공급자·자격 범위·이동수단·경로 옵션·출발 좌표·도착 좌표·차량 조건을 포함한다. A→B와 B→A를 분리한다. taskId와 이동시간 키를 분리해 같은 좌표의 서로 다른 업무는 유지하면서 이동시간만 재사용한다.

각 구간은 시간, 거리, 관측 시각, 옵션, 방향, 실제/추정/도달 불가/오류 상태를 가진다. 응답이 실패한 값을 0이나 영구 도달 불가로 저장하지 않는다. 단일 비정상 구간 때문에 기존 성공 구간까지 모두 버리지 않는다.

순서 캐시 키는 방문지의 원래 표시 순서에 영향을 받지 않도록 정규화한 집합과 시작점·고정 목적지·종점·모드·옵션·행렬 버전을 사용한다. 완료는 무조건 새 행렬 생성으로 취급하지 않는다.

도보 추천에서 받은 경로의 필요한 부분을 상세 미리보기에서도 재사용한다. 단, 구간 시간만 있는 차량 다중 API 결과를 상세 폴리라인이 있는 경로처럼 쓰지 않는다. 차량 SDK와 REST가 출입점/탐색 옵션을 다르게 쓸 수 있다는 점도 구분한다.

현재 운영 구간 캐시는 5분이다. 초기 구현에서 무조건 하루/영구 저장으로 늘리지 않는다. 제공사 저장 조건과 실시간 교통 유효성을 확인해 모드별 정책을 별도로 정한다. 유효기간이 지났다면 신규 조회가 생길 수 있으므로 '모드 전환은 항상 0회'라고 약속하지 않는다. 과거 순서는 초기 후보로 쓸 수 있지만 최신 교통 기준 최적해처럼 표현하지 않는다.

## 9. 비용·실패·동시성

- 추천 작업 전 필요한 묶음 수와 여유분을 계획하고 실제 전송 요청을 계수한다.
- 도보 추천과 도보 상세 안내가 같은 API 예산을 쓴다는 점을 반영해, 안내용 여유를 우선 확보한다.
- 다중 출발지/다중 목적지/개별 차량 경로/SDK는 구분해 관측한다. SDK 내부 호출을 서버 REST 계수로 다 안다고 가정하지 않는다.
- 개발자 키가 다른 서비스에서도 쓰이면 앱 내부 계수만으로 실제 남은 무료량을 알 수 없으므로 공급자 콘솔 통계와 맞춘다.
- 분당 보호 한도와 일일 무료 쿼터는 다르다. 현재 300회/분 보호만으로 과금을 막을 수 없다.
- 서버가 여러 대라도 일일 예산이 공유되도록 DB의 원자적 카운터/예약을 사용한다. 초기안에서 새 Redis 서버를 필수로 추가하지 않는다.
- 같은 구간을 여러 추천이 동시에 요청하면 하나의 진행 중 요청을 공유한다.
- 취소는 아직 전송하지 않은 요청부터 막는다. 이미 나간 요청이 취소됐다고 쿼터가 환급됐다고 가정하지 않는다.
- 요청 예산과 시간 제한을 실제 API 호출 직전에 확인한다. 현재 worker thread에 ThreadLocal 마감시간이 자동 전파될 것이라고 가정하지 않는다.
- 경유 묶음 실패는 제한된 횟수로 분리해 원인 구간을 확인한다. 429/권한 실패를 재시도 폭주나 무제한 개별 호출로 바꾸지 않는다.
- 계산 실패 시 지도와 목록은 유지한다. 유효한 같은 조건의 마지막 결과, 확인된 후보, 거리 추정 순서 순으로 사용하고 출처를 구분한다.

매 추천의 고정 호출 상한을 근거 없이 10/40으로 확정하지 않는다. 계획된 전체 묶음 수, 사용자·앱 잔여 예산, 상세 안내 예산을 합쳐 제한하고 실제 지연·품질 측정 후 배포 설정값을 고정한다. 한도가 낮아서 전체 행렬을 못 모으면 부분 전략임을 기록한다.

## 10. 정확도의 정의와 검증

서로 다른 문제를 분리해서 측정한다.

1. **수집 정확성:** 경유 묶음 leg와 동일 옵션 단일 구간 조회의 시간/거리/지점 대응이 일치하는가?
2. **순서 최적화 품질:** 같은 완전한 시간 행렬에서 최적/최선 기준과 얼마나 차이 나는가?
3. **실시간 예측 한계:** 조회 시점 교통으로 계산한 시간이 미래 실제 이동시간과 얼마나 다른가? 현재 작업시간/미래 출발 교통까지 최적화한 모델은 아니다.
4. **사용 안정성:** 안내 중 목적지 보존, 작은 개선으로 목록이 계속 흔들리지 않는가?
5. **비용:** 실제 요청과 쿼터 차감, 등록 누적/반복 전환/실패까지 포함한 하루 사용자 단위 사용량.

### 필수 시나리오

- 5곳·20곳, 차량·도보, 밀집/분산/산·하천 우회 구역.
- 최초 일괄 등록, 20초 간격 개별 등록, 새 방문지 추가, 삭제, 완료, 다른 곳 우선 안내.
- 모드 10회 왕복 전환, 현재 위치 이동, 캐시 만료, 근무지 복귀 포함/제외.
- 같은 좌표의 서로 다른 업무, 반대 방향 이동시간 차이, 도달 불가, 경유 실패, 네트워크 제한, 여러 사용자 동시 요청.
- 경유 묶음 전체 20곳 검증. 5곳 결과만으로 전국/20곳 등가성을 주장하지 않는다.

5곳은 완전한 실제 행렬에서 정확해와 일치하는지 확인한다. 20곳은 오프라인 DP/CP-SAT 등으로 기준을 만든다. 최적 증명을 못 끝내면 '최적해 대비 오차' 대신 최선의 기준 대비 차이와 하한을 구분한다. 기존 20곳 알고리즘보다 빠르다는 결과만으로 정확도가 증명됐다고 하지 않는다.

완전 행렬 방식은 같은 원래 시간 행렬로 기존 순서도 함께 평가해서 더 나쁜 결과를 반환하지 않는 검사부터 넣는다. 이 보장은 동일 지점·시작점·종점·제약·시각 기준의 비교에 한정한다. 새 지점 추가나 교통 갱신으로 문제가 달라지면 과거 총시간과 단순 비교하지 않는다.

부분 행렬 전략의 출시 목표는 완전 행렬 기준에 대한 평균/상위 95%/최악 시간 증가량과 호출 절감량으로 별도 정한다. 예컨대 평균 2%, 상위 95% 5% 이내를 목표로 시험할 수 있으나 이는 **미달이면 조정할 시험 목표**이며 현재 보장값이 아니다.

### 이번 확인으로 말할 수 있는 범위

- 기존 비교에서 도보 20곳의 절약 시제품이 더 짧았다는 것은 기존이 근사 방식임을 보여준다. 어느 쪽의 전역 정확도도 증명하지 않는다.
- 5곳의 25구간을 6회로 수집해 모두 같은 값을 얻은 것은 정보 보존형 절감 가능성의 실제 증거다.
- 20곳 72묶음은 요청 계획이고 실제 72회 응답 검증/추천 품질 측정은 아직 하지 않았다.
- OR-Tools가 우리 20곳 자료에서 얼마나 개선하는지는 통합 후 같은 행렬로 측정할 항목이며, 지금 성능 수치를 만들어 제시하지 않는다.

## 11. 구현 단위

1. `RoadTimeStore`: 방향별 실제 구간·유효기간·진행 중 요청 공유.
2. `KakaoMatrixBatchPlanner`: 차량 행/열, 도보 경유 체인, 캐시 누락만 계획.
3. `KakaoWalkingClient`: 경유 요청과 leg별 파싱을 기존 상세 경로 계약과 분리해 확장.
4. `VisitOrderSolver`: DP/OR-Tools, 고정 첫 방문지/열린 경로/복귀 종점, 기존 순서와 검증된 최선 보존.
5. `RecommendationCoordinator`: 변경 사건·버전·예산·작업 큐·취소·폴백을 관리.
6. `RouteService`/`RouteRequestGuard`/`ProviderQuotaInterceptor`: 상세 경로 재사용, 정규화 키, 실제 요청 계수, worker에 전달되는 마감/예산.
7. `MapScreen.js`/`visitOrder.js`: 완료·안내 상태만 바뀌어도 전체 재추천하는 effect를 사건별 호출로 교체. UI 구조와 자동 추천은 유지.
8. 비교 하네스: 기존 단일/새 묶음 동일 데이터 수집 검사와 전체 행렬 기준 품질 비교를 분리.

구현은 위 데이터 계약·예산·불변 조건을 한 설계로 진행하고, 기능 플래그 아래서 기존 결과와 비교한 뒤 전환한다. 기존 정확도를 따로 고쳐놓고 또 전면 개편하는 이중 작업을 하지 않는다.

## 12. 재현 자료

- `tools/compare-route-recommendations.py`: 기존/부분 조회 시제품 비교.
- `tools/RouteComparisonReplay.java`: 현재 운영 서비스 결과 재생 검증.
- `tools/plan-walking-batches.py`: 5곳 25구간/20곳 400구간의 묶음 계획 및 빠짐·중복 검사. 외부 호출 없음.
- `tools/probe-route-batching.py`: 제한된 실제 경유/다중 출발지 계약 확인. 기본 3요청, `--matrix-five`는 도보 6회, `--repeated-waypoint`는 도보 2회다.
- `tmp/route-comparison/batching-probe.json`, `batching-five-matrix-probe.json`, `batching-repeated-probe.json`, `batch-plan.json`: 원시 검증 결과. API 키를 저장하지 않았다.

운영 추천 코드·의존성·배포는 변경하지 않았다. 이번 작업은 조사, 설계, 별도 검증 도구와 문서 작성이다.
