PANG3 모바일 UX 심층분석 — Codex 독립 조사
확인일: 2026-10-13, Asia/Seoul
분석 상태: 조사 완료. 구현·업무 정책 확정·사용자 테스트는 수행하지 않음.

1. 요약: 현재 UX의 핵심 흐름과 가장 먼저 풀 후보

PANG3는 지도에서 방문지를 관리하고, 한 목적지의 차량/도보 경로를 확인한 뒤 사진·메모·처리 상태를 기록하고 HWPX 보고서를 확인하는 모바일 외근 도구다. 개인 업무공간과 공유 그룹이 있고, 공유 그룹에서는 팀원 현황·초대·업무 이관·그룹 보고서를 볼 수 있다. 그룹 리더/구성원 구분과 배정 API는 존재하지만, 별도 AssignmentScreen으로 들어가는 현재 모바일 진입점은 발견하지 못했다. 따라서 “배정 화면을 매일 이용하는 관리자”를 확인된 모바일 사용자로 간주하지 않았다.

현재 UI를 전면 교체할 근거는 없다. 우선 해결할 문제는 화면의 모양보다 기록과 상태의 연결이다. 사진을 이어 저장했는데 최신 보고서에서 기존 사진이 빠질 가능성, 일부 이탈 경로에서 작성 내용을 잃는 문제, 저장 성공과 업무 완료·AI 문서 준비가 섞인 문제, 여러 방문지 선택과 실제 열리는 파일의 범위가 다른 문제가 코드에서 확인된다. 위치 취득 실패가 지도 표시 전체를 막는 구조도 외근 시작을 지연시킬 수 있다.

최우선 추천 5개:
1) F02 사진의 전/중/후 구분과 기존 사진 유지: 업무 증거의 신뢰성에 직접 영향을 준다.
2) F01 모든 화면 이탈 경로에 작성 보호 적용: 이미 있는 확인 절차를 확장하는 비교적 작은 변경이다.
3) F03 저장·업무 완료·문서 준비 상태 구분: 저장했지만 파일이 없는 상황과 긴 대기를 설명해야 한다.
4) F04 선택한 방문지와 열리는 보고서 파일 일치: 다중 선택 결과가 첫 파일로 축소되는 현재 동작을 바로잡는다.
5) F05 현재 위치 실패와 지도/업무 조회 분리: 위치를 얻지 못해도 이미 알고 있는 업무를 확인할 수 있게 한다.

이 순위는 실제 사용 빈도 측정값에 기반한 순위가 아니다. 현장에서 사진을 이어 저장하고, 여러 업무를 다루며, 네트워크/GPS가 불안정할 수 있다는 임시 가정 아래 기록 신뢰성과 회복 비용을 우선했다. 실제 사진 재편집 빈도가 낮으면 F04·F05 또는 F06의 순위가 올라갈 수 있다. 소요 시간 절감·만족도 향상을 실증했다고 주장하지 않는다.

조사 방식은 정적 코드 분석과 실제 웹 검색/원문 확인이다. 앱을 실행하거나 실제 단말을 조작하지 않았다. 화면 스크린샷을 직접 관찰하지 않았으며, 마찰의 정도·야외 가독성·제스처 충돌·플랫폼별 실행 성공은 코드상 추정이다. APK/배포 앱의 실제 진입점과 이 커밋의 일치 여부도 미확인이다. frontend/app/의 Expo Router 샘플이 배포 앱에 사용된다고 단정하지 않았다. 요청이 지정한 App.js와 그 import/콜백을 따라 분석했다.

web/의 화면·라우팅·관리자 기능·앱/웹 연계는 제외했다. backend는 모바일 저장·보고서·배정/이관 권한·경로 응답을 확인하는 부분만 읽었다. ai는 관련 Java 호출 계약으로 제약을 확인했고 Python 전체나 인프라를 조사하지 않았다. 운영 서비스에 접속하거나 실제 데이터·사진·위치 원본을 읽지 않았다. .env·AWS 설정·인증키 값은 읽지 않았다. 의존성 설치·빌드·전체 테스트·배포·Git 상태 변경은 하지 않았다.

4. 모바일 역할·활성 화면·상태·사용자 여정 지도

4-1. 구현으로 확인되는 역할
개인 담당자: 개인 업무공간에서 자기 방문지·경로·현장 기록을 관리한다.
공유 그룹 구성원: 자기 담당 업무를 지도에서 수행하고 다른 구성원에게 이관 요청하거나 받은 요청을 처리하며 팀 현황을 본다.
그룹 리더: backend GroupService.java:31, 71-96, 419-474에서 LEADER와 배정 권한을 확인했다. 구성원과 동일한 모든 모바일 과업을 수행한다고 단정하지 않는다. 특히 배정 화면 진입은 미확인이다.
초대는 리더 전용으로 가정하지 않았다. GroupService.java:318-354의 inviteMember는 requireMember로 구성원을 확인한다. 현장 기록 저장은 TaskProgressService.java:147-157에서 현재 담당자 여부와 완료 상태를 검사한다. 이 확인은 유지할 단계다.

4-2. 활성 화면 연결
LoginScreen → RegisterScreen: 가입 후 로그인. LoginScreen 성공 → App.js:908-930의 mapDirect. 저장된 그룹을 복구한다.
mapDirect → MapScreen/NormalMapScreen: 지도 표시, 행정동 선택, 방문지 목록, 주소 검색/지도 선택/좌표 등록, 공공시설물 등록, 미처리 업무 추가, 한 목적지 경로 미리보기/안내, 복귀 목적지.
지도 대상 → FieldActionScreen: 미완료 대상의 사진·위치도·메모·상태 기록. 완료 대상 → ReportScreen 조회.
하단 보고서 → ReportListScreen → FieldActionScreen 또는 ReportScreen → DownloadScreen. ReportScreen은 신규 문서 생성 버튼을 실행하는 화면이 아니라 저장된 progress를 조회하는 미리보기다.
하단 그룹 → GroupScreen → 현재 선택 그룹이면 GroupWorkspaceScreen(공유)/WorkStatusScreen(개인). 다른 그룹 첫 선택은 activeGroup만 변경하고 GroupScreen에 남는다.
GroupScreen → GroupCreateScreen/GroupInvitationsScreen → GroupWorkspaceScreen.
GroupWorkspaceScreen: dashboard 탭의 WorkStatusScreen, transfer 탭의 팀원/받은 요청, settings 탭의 팀원·보고서·알림 설정. 팀원 관리 → GroupDetailScreen(mode=members), 팀원 이관 → TransferScreen, 그룹 보고서 → GroupReportsScreen → DownloadScreen.
하단 대시보드 → DashboardScreen: 전체 업무 통계·월간 완료 히트맵·요일별 현황. 설정 → SettingsScreen. App.js:945-949는 user만 전달하며 activeGroup은 전달하지 않는다. 이를 “현재 그룹의 오늘 업무 홈”으로 해석하지 않는다.

활성 여부 주의:
AssignmentScreen은 import와 조건부 렌더링(App.js:1133-1144), API 호출이 있지만 go('assignment') 진입 콜백을 찾지 못했다. teamLocations의 openTeamMap 함수는 정의되어 있으나 실제 호출 지점을 찾지 못했다. publicDataAssignment도 렌더링은 있지만 실제 진입을 찾지 못했다. groupDetail(mode=all)의 기존 관리 흐름도 정상 진입점이 확인되지 않았다. groupSettings로 보내는 prop은 GroupWorkspaceScreen이 받거나 사용하지 않는다.
MainScreen.js, GroupDashboardScreen.js, PublicDataAssignmentScreen.js, PublicDataMapMode.js는 App.js의 활성 import/연결로 확인되지 않았다. 미사용·이전 흐름 후보로 구분했다. 파일이 존재한다는 이유로 현재 UX 문제나 기능을 부풀리지 않았다.

4-3. 핵심 여정
J1 현장 담당자: 로그인 → 복구된 업무공간 지도 → 오늘 지도 방문지/미처리 업무 확인 → 대상 선택 → 경로 미리보기 → 안내 시작 → 이동 → 대상 카드/마커 → 현장 기록 → 사진·메모·상태 → 보고서 저장 → 진입한 화면으로 복귀 → 다음 대상 선택. 종료 조건은 사용자 선택 상태가 서버에 저장되는 것이다. 안내 종료나 도착 자체는 업무 완료가 아니다.
J2 보고서 확인: 보고서 목록 → 진행 중/완료 방문지 선택 → 보고서 미리보기 → 파일 화면 → HWPX 외부 지원 앱/브라우저 열기 → 앱 복귀. 현재 “제출/발송” 실행은 이 활성 흐름에서 확인하지 못했다. 파일 열기를 제출로 설명하지 않는다.
J3 그룹 맥락: 그룹 목록 → 그룹 선택 → 필요시 같은 그룹 재선택 → 그룹 업무현황 → 지도/보고서. 그룹을 바꾸면 행정동·경로·목록을 초기화하고 새 업무공간의 저장 상태를 읽는다.
J4 이관: 그룹 업무 이관 → 수신 팀원 → 본인 미완료 방문지 선택 → 요청 → 상대의 수락/거절 → 수락된 방문지를 수신자의 미처리 업무에서 오늘 지도에 추가. “담당자 변경”과 “오늘 지도에 편입”은 별개다.
J5 초대: 그룹 생성 또는 기존 그룹 팀원 관리 → 로그인 ID 입력 → 초대 → 수신자의 받은 초대 → 수락 → 그룹 업무공간. 초대 발송은 실제로 수행하지 않았다.
J6 배정: 서버 및 별도 화면에 구현은 있으나 활성 앱 진입 미확인. 현행 모바일 여정으로 확정하지 않고 F14에서 다룬다.

4-4. 상태와 공급자
업무 상태: pending/working/complete. 지도·현장 기록은 작업 전/작업 중/작업 후, 보고서는 진행 전/진행 중/완료처럼 서로 다른 문구를 사용한다.
오늘 지도 포함 여부: workPlan의 choices[assignmentKey]와 날짜·배정 시각, 미처리 목록으로 결정. 이관 수락 ID는 명시 선택 전까지 별도로 보류된다.
경로: destinationKey로 한 목적지를 추적한다. restoreRouteSession은 같은 날의 유효한 미완료 목적지만 복구한다. 과거 다중 구간 경로를 현재 UI에서 재개하지 않는다.
현장 기록: task-progress의 새 progress 저장과 task 상태 갱신. 문서: AI 생성 결과에 reportFilePath가 있어야 reportDownloadUrl이 나온다. 저장된 기록과 파일 존재는 동일하지 않다.
지도 표시/검색/역지오코딩: Kakao 지도 WebView·Kakao local API. 위치 취득: expo-location foreground permission, getCurrentPositionAsync, watchPositionAsync.
현재 경로 계산 진입: MapScreen.js:1105-1126 → /api/routes/segment → RouteService.java:560-573. 차량은 Kakao Mobility directions, 도보는 KakaoWalkingClient 경로. 다른 도보 함수/서비스 코드가 존재해도 현재 단일 구간 분기에서 사용한다고 단정하지 않는다.
차량 내비게이션: Android에서 모듈 사용 가능 시 앱 내부 KakaoNavigationView/KNSDK를 올린다(MapScreen.js:1257-1262, 1345-1356). iOS 및 모듈 미지원은 동일 네이티브 뷰가 아닌 지도 안내 상태로 처리된다. tmap 브랜치명은 TMAP 연동의 근거가 아니다. 이 흐름에서 외부 TMAP/카카오내비 앱 실행은 확인되지 않았다. 실제 SDK 연결 성공은 미실행 상태다.
알림: 수신 시 일부 업무 유형을 새로고침하고 탭 시 main으로 이동한다(App.js:756-790). main은 현재 DashboardScreen 렌더링이다.

5. 현재 잘 작동하는 점과 유지할 요소

A/C: 일반 지도는 App.js:1184-1249의 지속 마운트 레이어로 다른 화면에서도 유지한다. 지도/기록 왕복 때 매번 지도를 재생성하지 않으려는 구조다. 숨긴 지도는 pointerEvents와 접근성 노출을 차단한다. “지도는 항상 초기화된다”는 일반 진단은 맞지 않는다.
A/C: 작업공간별 목록·작업계획·경로 캐시와 요청 버전 확인이 있다(App.js:282-420, 484-498). 이전 요청이 최신 그룹/경로를 덮는 것을 방지하는 장치는 유지한다.
A/C: restoreRouteSession은 서버 업무 상태를 기준으로 완료/삭제된 목적지 안내를 복구하지 않는다. 같은 날만 복구하고 사용자/그룹별 저장 키를 쓰는 방향은 합리적이다.
A/C: 경로 미리보기는 현재 안내를 확정하지 않는다. 안내 시작의 경로 계산이 성공한 뒤에 순서/상태를 변경한다(MapScreen.js:1190-1266). 둘을 합쳐 마커 터치만으로 업무나 안내가 시작되도록 바꾸지 않는다.
A/C: 현장 기록의 헤더 뒤로가기·Android 뒤로가기에 변경 확인과 저장 중 이탈 안내가 있다(FieldActionScreen.js:485-511). 삭제/완료/이관 책임 확인을 클릭 수 감소를 이유로 제거하지 않는다.
A/C: 이관은 수신자 수락과 서버의 현재 담당자·완료 여부 확인을 거친다. 실패해도 요청/업무 책임이 어디에 있는지를 설명하는 기존 방향은 유지한다.
A/C: 공공시설물과 주소·직접 위치 선택, 사진 편집/위치도 편집, 음성 메모 입력은 현장 과업에 맞는 기존 수단이다. 새 기능을 늘리기 전에 이 수단들의 기록 보존과 복귀를 다듬는다.

7. UX 이슈 목록 F01…와 근거·현재/개선 흐름

F01. 작성 보호가 일부 화면 이탈에만 적용됨

C 부담: 안전한 “뒤로가기”와 다른 이탈의 결과가 달라 사용자가 저장됐다고 오해하거나 다시 사진/메모를 작성할 수 있다. 저장 중 이탈은 응답 전후 복귀 흐름도 불확실하게 만든다.

F02. 사진을 이어 저장할 때 최신 기록의 사진 보존과 전/중/후 매핑이 불안정
여정/상황: J1 작업 전 사진 저장 후 다시 열어 작업 중 사진만 추가하거나, 작업 후 사진만 있는 기록을 재개한다.
A 근거: FieldActionScreen.js:605-629는 fieldPhotos[index]를 PHOTO_TYPES의 순서에 매핑한다. 1142-1174는 file://·content://의 새 로컬 사진만 업로드한다. TaskProgressService.java:44는 새 TaskProgress를 생성하고 60-80은 이번 업로드 목록만 fieldPhotos로 저장한다. 135-140의 조회는 최신 progress 하나를 반환한다. 서버 사진 경로는 photo+i이고 사진 type은 이 저장 구조에 별도 필드로 보존되지 않는다. 라벨은 comment 문자열에 붙지만 모바일 로드는 이를 type으로 해석하지 않는다.
C 구체 결과: 기존 원격 사진에 메모만 변경하면 새 업로드가 없어 최신 progress의 사진 목록이 비는 코드 경로가 있다. 작업 후 사진 한 장만 전송하면 재조회 시 배열 0번이 작업 전 칸에 놓인다. 이전 progress/파일이 물리적으로 삭제된다고 단정하지 않는다. 문제는 최신 조회/생성 보고서에서 기록의 의미와 연속성이 달라지는 것이다.
유형: 구현 오류/데이터 계약. 사용자가 느끼는 피해 D 미확인이나 근거는 강함.

A 근거: App.js:31, 1133-1144는 AssignmentScreen을 포함한다. AssignmentScreen.js:305-435는 배정/동 배정/해제를 구현하고 GroupService.java:419-474는 리더 검증을 포함한다. 그러나 App.js의 go 호출과 활성 GroupWorkspace/GroupDetail(members) 콜백에서 assignment 진입이 확인되지 않았다. openTeamMap도 호출 연결 미확인이다.

유형: 활성 연결 미확인/업무 범위 가설. “배정 기능이 고장났다”로 확정하지 않는다.
B 외부 근거: 기업용 배정 앱의 기능 소개는 PANG3 모바일 배정 필요성을 증명하지 않는다. 직접 대응 근거 없음.
최소안: 배포 앱에서 진입점과 역할을 먼저 관찰한다. 모바일 배정이 필요하다고 확인되면 리더에게 기존 배정 화면으로 명시 진입을 제공하되 기존 화면의 데이터/권한/부분 실패를 함께 검증한다.
대안: 모바일 배정 신규 기능을 만들지 않고 현재 현장 조회·수락·이관에 집중. 실제 역할 정의가 이 경우라면 추천.
전(가설): 그룹 현황 → 최초 배정 경로 탐색 → 진입 미확인.
후(조건부 제안): 리더 그룹 현황 → 업무 배정 → 대상/담당자 검토 → 배정 → 결과 확인.
영향/위험: App 라우팅·GroupWorkspace·Assignment·서버 리더 권한. 미사용 코드를 바로 노출하면 오래된 흐름 회귀 가능. 권한 검증 제거 금지.
답변 의존: Q6 필수.
확신도/검증: 이 소스의 호출 부재 높음, 배포 앱/업무 필요성 낮음. V4에서 실제 리더 진입 관찰 후 판단.

8. 공통 원인과 개선 방향, 추천안과 기각한 대안

C 공통 원인 1: 화면마다 이동을 직접 실행하여 폼/조회 맥락의 수명이 다르다(F01/F06/F10). 사용자가 돌아갈 목적 화면과 유지할 상태를 명시하는 작은 변경이 필요하다. 내비게이션 프레임워크 교체를 UX 해결책으로 제안하지 않는다.
C 공통 원인 2: 기록 저장, 업무 상태, 문서 생성, 파일 열기가 한 성공 느낌으로 묶인다(F02/F03/F04/F08). 상태 모델을 사용자에게 보이는 사실에 맞춰 구분해야 한다. 기술 리팩터링이 아니라 “어떤 내용이 어디까지 저장됐는가”를 보여주는 것이 목표다.
C 공통 원인 3: 다음 행동이 문구와 실제 이동 사이에서 끊긴다(F07/F12/F14). 받은 업무/현재 목적지의 맥락을 재탐색하지 않고 이어갈 행동을 기존 화면에 붙인다.
C 공통 원인 4: 실패가 빈 결과/일반 경고/동일 재시도로 축약된다(F05/F08/F09/F13). 사용자가 지금 가능한 과업과 재시도 대상만 정확히 파악하게 한다.

주요 판단 D01-D08. 이 D번호는 다른 모델과 자동 대응하지 않는다.

9. 우선순위·의존성·점진적 실행 순서

9-1. 작은 범위로 먼저 검증할 개선
F01 모든 이탈 보호(작음~중간): 기존 확인 UI 재사용, 앱 이동/제스처/알림 연결 때문에 화면 하나 수정보다 넓다. 선행은 dirty/saving 판단의 공유 방법 확정. 실패 위험은 중복 확인과 저장 중 콜백 경합. 완료 기준: 변경 후 모든 이탈에서 계속 작성/명시 폐기 가능, 저장 중 데이터·중복 저장 보호. 강제 종료 회복은 이 단계 범위 밖.
F04 파일 범위/준비 안내(작음~중간): Report/Download 결과와 개별 파일 표기. 선행은 대상/문서 상태 정의. 위험은 다중 선택 상태/파일 연결. 완료 기준: 선택 N건과 파일 M건 일치, 없는 URL에 준비 완료 표시 없음, 조회 실패 재시도 가능.
F06 카드 행동 설명 또는 한 행동 진입(작음): 그룹 선택 직후 로딩·오류 포함. 선행 Q4 확인 또는 현장 시안 비교. 완료 기준: 사용자가 현재 그룹과 진입 결과를 설명할 수 있음.
F07 수락 안내 문구 일치(작음): 자동 편입 제외. 완료 기준: 두 수락 지점이 같은 실제 다음 행동 안내.
F11 효과 없는 알림 스위치 정리(작음): 실제 제어 구현은 중간 이상. 완료 기준: 적용되지 않는 선택을 저장된 설정처럼 보여주지 않음.
F13 로그인 실패 구분(작음): 완료 기준: 인증/연결 실패 각각 입력 유지와 적합한 재시도 안내.

9-2. 관련 흐름을 함께 고쳐야 효과가 나는 개선
F02 사진 의미/보존(중간): 모바일·서버·AI 입력 계약·기존 자료 호환까지 영향. 선행은 최신 기록의 누적/스냅샷 의미 확인. 실패 위험 가장 큼. 완료 기준: 전/중/후 단독·조합, 원격 사진 유지, 메모만 수정, 명시 삭제가 재조회와 문서에서 일치. 이전 이력은 별도로 보존됨을 확인.
F03 저장 결과/완료 설명(중간): 서버와 화면 간 상태 계약이 필요. 비동기 생성은 큼: job·재시도·중복 제어·완료 후 재생성 추가. 선행 F02 계약과 Q2. 완료 기준: 기록 저장·업무 완료·문서 실패를 각각 식별하고 이미 저장된 내용을 안전하게 확인할 수 있음.
F05 GPS와 지도 분리(중간): 초기 지도 source/중심/경로 재개에 영향을 줌. 선행 데이터 중심과 실제 GPS 모델 분리. 위험은 잘못된 출발점. 완료 기준: 위치 거부/지연에도 알고 있는 업무 조회 가능, GPS 없는 안내는 제한, 복귀 시 위치 갱신 확인.
F08 조회/캐시 상태(중간): App 결과 모델부터 Map/ReportList/GroupWorkspace까지 전달. 선행 상태 정의. 완료 기준: 캐시·실제 빈 결과·실패·일부 실패가 구분됨.
F09 부분 등록 결과(중간): 로컬 합병·서버 확인/재시도. 완료 기준: 중간 실패 때 성공분과 미완료 대상을 식별, 미확인 POST는 확인 후 처리.
F10 보고서 조회 맥락 유지(작음~중간): F04와 함께 진행. 완료 기준: 파일 왕복 후 동일 필터/선택/스크롤, 다른 그룹 전환 시 오래된 선택 없음.
F12 기록 행동 명시(작음~중간): 목적지 카드/마커 행동/네이티브 안내 복귀까지 확인. 완료 기준: 처음 쓰는 담당자가 도움 없이 현장 기록으로 진입하고 완료/복귀 목적지 예외를 이해.

9-3. 사용자 결정·현장 검증 후 판단
F01 로컬 초안/기기 재실행 복구, F03 비동기 문서/완료 후 수정, F04 통합 문서, F05 수동 출발/오프라인 전송, F07 자동 지도 편입, F11 필수 알림 제어, F14 모바일 최초 배정.
이들은 기존 흐름 설명·보존 수정과 구분되는 신규 기능 또는 정책 변경이다. 조사 요청을 구현 권한으로 해석하지 않는다.

추천 실행 순서(미래 구현 제안):
먼저 F02 사진 실패 경로의 테스트 자료/계약과 F01 이탈 보호 범위를 정의 → F01 최소 보호와 F02 보존 수정 → F03 결과 상태/F04 파일 일치 및 F10 복귀를 함께 검증 → F05/F08 위치/조회 실패 회복 → F06/F07/F12 다음 행동 연결 → 실제 빈도에 따라 F09/F11/F13 → 정책 답변 이후 신규 기능/F14.
F02/F01 검증은 독립적으로 착수할 수 있으나 F03의 안전한 누적 저장은 F02 의미 결정에 의존한다. 빠른 문구 수정(F07/F13 등)은 앞 단계와 독립적이다. 개발 기간/일수는 산정하지 않았다.

10. 추천안의 과업별 검증 계획

다음은 제안한 미래 테스트다. 이번 조사에서 실행하지 않았다. 운영 자료 대신 비식별 테스트 방문지·사진을 사용한다. 사용자에게 실제 업무를 생성/발송시키는 연구를 지금 수행하지 않는다. 복잡한 계측 도구 없이 화면 녹화 또는 관찰 메모와 성공/실패·왕복·재입력 수로 비교할 수 있다.
현재 측정 기준선: 없음. 기존 구현과 개선 시안을 같은 과업으로 비교해야 한다. 아래 완료 기준은 제안 목표이며 입증된 성과가 아니다.

V1 현장 기록을 이어 쓰고 중단 후 돌아오기 — F01/F02
시작 조건: 미완료 자기 담당 방문지, 작업 전 사진이 저장된 기록, 다른 미완료 방문지 1개.
과업: 작업 중 사진/메모 추가 → 하단 지도 이동 시도 → 계속 작성 → 저장 → 재진입 → 메모만 수정 → 저장 → 사진/라벨 확인.
관찰: 사진 재촬영 요구, 기존 첨부 누락, 전/중/후 오배치, 이탈 확인 우회, 목적 화면 복귀.
완료: 유지한 사진·수정 메모·각 단계가 최신 조회/문서와 일치, 명시 폐기 외에는 이탈로 입력이 사라지지 않음.
예외: 후 사진만 촬영, Android 뒤로가기, iOS 스와이프, 알림 탭, 저장 중 이동, 권한 거부. 로컬 초안 대안은 별도 앱 강제 종료/재실행으로 검증.
측정: 과업 성공, 재촬영/재입력 수, 원하지 않은 이탈 수, 복구 여부.

V2 업무 완료와 문서 확인 — F03/F04/F10
시작 조건: 진행 중/완료 방문지 여러 개, 파일 준비·파일 없는 기록·조회 실패를 포함한 테스트 응답.
과업: 작업 후 상태 저장의 효과 설명 → 결과 확인 → 3개 대상 선택 → 각 파일 확인 → 목록 복귀 → 날짜/담당자 필터로 그룹 파일 확인.
관찰: 저장=제출 오해, 첫 파일을 통합으로 오해, 완료 후 편집 불가의 surprise, 선택/필터 초기화.
완료: 사용자 설명이 실제 저장/완료/파일 상태와 일치, 파일 없는 대상을 식별, 복귀 맥락 유지.
예외: AI 실패, 일부 GET 실패, 저장 응답 유실, HWPX 지원 앱 없음/외부 앱 복귀, 완료 후 자료 수정 요청.
측정: 올바른 파일 선택, 상태 설명 정확성, 왕복·재입력 수, 중복 저장 시도. AI 시간을 측정하더라도 실제 네트워크/사진 조건을 같이 기록.

V3 위치·네트워크 실패에서 가능한 업무 유지 — F05/F08/F09/F13
시작 조건: 기존 업무 캐시 있음/없음 두 조건, GPS 느림/권한 거부, 제어 가능한 테스트 네트워크.
과업: 로그인/업무 조회 → 위치 실패 상태에서 방문지 확인 → 권한 복구 후 안내 → 갱신 실패 후 최신성 확인 → 시설물 여러 개 등록의 두 번째 요청 실패 결과 확인.
관찰: 잘못된 비밀번호 재입력, 무한 위치 대기, 캐시를 최신으로 오해, 일부 성공 후 전체 재시도.
완료: 장애 원인에 맞는 행동, 위치와 업무 조회 분리, 성공/실패 대상과 캐시 상태 설명 가능.
예외: 대략적 위치, 위치 서비스 꺼짐, 백그라운드 복귀, 지도 자체 네트워크 실패, POST 응답 유실.
측정: 과업 유지/회복 성공, 동일 재시도 반복 수, 성공분 재등록 시도, 잘못된 안내 출발 여부.

V4 그룹과 이관 맥락 — F06/F07/F11/F14
시작 조건: 개인/공유 그룹 2개, 이관 대기 요청, 일반 구성원/리더 테스트 역할.
과업: 다른 그룹 현황 열기 → 받은 업무 수락 → 오늘 지도에 명시 추가 → 그룹 알림 설정 확인 → 리더의 최초 배정 진입 관찰.
관찰: 같은 카드 재터치, 수락과 일정 편입 혼동, 다른 그룹의 업무/경로 혼입, 적용되지 않는 알림 선택, 배정 경로 존재 여부.
완료: 현재 그룹·담당자·오늘 포함 여부를 설명, 수락한 업무로 정확히 연결, 설정 효과가 표기와 일치.
예외: 수락 직전 업무 완료/담당자 변경, 느린 그룹 조회, 재실행, 이관 거절.
측정: 화면 탐색/왕복 수, 의도한 그룹 진입 성공, 담당자 변경/일정 편입 오해, 권한 거부의 이해.

V5 이동 종료 후 한 손으로 기록하고 다음 업무 선택 — F05/F12
시작 조건: 실제 사용 단말/글자 크기, 차량 안내 가능 Android와 지원하지 않는 조건, 안전하게 정지한 현장 유사 환경.
과업: 현재 목적지 확인 → 안내 종료/지도 복귀 → 현장 기록 찾아 사진·메모 저장 → 다음 방문지 선택.
관찰: 카드 주소 터치 발견, 같은 마커 반복에 따른 의미 변화, 차량/도보/종료 오조작, 뒤로가기 충돌, 남은 업무 찾기.
완료: 도움 없이 기록 진입/복귀/다음 대상 선택, 도착/안내 종료와 업무 완료를 혼동하지 않음.
예외: 지도 팬/확대, 키보드 표시, 큰 글자, 네이티브 안내 오류, 완료 대상/복귀 목적지 선택.
측정: 다음 행동을 못 찾는 구간, 잘못된 터치, 화면 왕복, 과업 성공. 이동 중 운전 조작 테스트는 수행하지 않음.

11. 사용자에게 나중에 받을 질문

지금 답하지 않아도 된다. 우선 질문 5개는 Q1-Q5이며, 정책 변경을 확정하기 전 Q6-Q9도 해당 범위에서 필요하다. 코드로 확인할 수 있는 동작은 질문으로 떠넘기지 않았다.

Q1 [우선/실제 사용자·빈도] 하루 업무에서 가장 자주 하는 흐름은 무엇이며, 사진을 여러 차례 이어 저장·공공시설물 다건 등록·복수 보고서 확인 중 실제 반복되는 것은 무엇인가?
이유: 빈도 없는 임시 우선순위를 조정.
연결: F01/F02/F04/F09/F12.
답에 따른 변경: 이어 기록이 많으면 F02 우선, 조회 중심이면 F04/F10, 등록 중심이면 F09 상승.
임시 가정: 여러 방문지를 다루고 기록을 작업 전/중/후로 이어 쓰는 담당자가 있음.
미답변 시 보류: 빈도 기반 효과/작업 시간 절감 추정과 역할별 최종 순위.

Q2 [우선/업무 정책] “작업 후/완료”는 실제 조치 종료, 보고서 작성 완료, 검토 완료 중 무엇이며 완료 뒤 사진·메모 수정은 누가 언제 할 수 있어야 하나?
이유: 현재 완료는 편집 불가와 연결됨.
연결: F02/F03.
답에 따른 변경: 별도 확정 단계·재개/정정 권한 또는 현재 정책 유지.
임시 가정: 완료 자료 수정 금지와 담당자 책임을 유지.
미답변 시 보류: 완료 후 편집 허용, 완료 자동 선택, 저장/완료 API 정책 변경.

Q3 [우선/핵심 과업·보고 정책] 보고서는 방문지별로 확인/제출하는가, 하루·담당자·그룹별 통합 문서가 필요한가? 파일을 연 뒤 실제 업무 종료까지 어떤 확인이 남는가?
이유: 다중 선택과 첫 파일 불일치를 통합 기능으로 풀어야 하는지 판단.
연결: F03/F04/F10.
답에 따른 변경: 개별 파일 목록 유지 또는 조건부 통합 생성, 기본 조회 기간.
임시 가정: 현 구현처럼 progress별 파일을 정확히 확인하는 것이 우선.
미답변 시 보류: 통합 양식/제출·공유 자동화, 파일 열기를 업무 종료로 간주.

Q4 [우선/작업 맥락] 개인/공유 그룹을 바꿀 때 바로 해당 현황을 여는 것이 자연스러운가? 이관을 수락하면 오늘 수행할 일까지 수락한 것인가, 담당자만 변경된 것인가?
이유: 그룹 카드 한 행동과 이관 지도 편입을 함께 판단.
연결: F06/F07.
답에 따른 변경: 그룹 선택/열기 분리, 한 행동 진입, 자동/명시 편입.
임시 가정: 그룹 선택 후 현황을 보며 이관의 일정 편입은 명시 선택.
미답변 시 보류: 수락 즉시 오늘 지도 자동 추가, 그룹 전환 시 진행 업무 종료.

Q5 [우선/현장 환경] 실제 단말·OS, 차량/도보 비중, 실내 출발·야외 밝기·장갑/한 손 사용, 통신 단절과 GPS 불안정은 어떤 상황에서 발생하는가? 기록 좌표에 요구되는 정확도는 어느 정도인가?
이유: 위치 실패·내비게이션·초안/오프라인·터치 영역의 우선순위를 판단.
연결: F01/F05/F08/F12.
답에 따른 변경: 플랫폼 검증 순서, 위치 상태 안내, 필요시 초안/전송 큐 또는 수동 출발지.
임시 가정: 위치를 못 얻어도 기존 업무 조회는 가능해야 하며, 실제 현재 위치를 임의로 만들지 않음.
미답변 시 보류: 완전 오프라인 지원, GPS 정확도 임계값, 수동 출발/자동 도착 정책.

Q6 [역할·범위] 그룹 리더가 모바일에서 처음 업무를 배정해야 하는가, 아니면 모바일은 자기 업무 수행·이관 중심인가?
이유: 실제 배포 진입 관찰로 배정 링크 부재를 확인한 뒤 범위를 결정.
연결: F14.
답에 따른 변경: 기존 AssignmentScreen 검증/연결 또는 모바일 배정 제외.
임시 가정: 현재 연결이 확인된 현장 흐름을 우선.
미답변 시 보류: 배정 화면 신규 진입·새 관리 기능, 역할/권한 확대.

Q7 [업무 정책] 이관받은 업무의 예정일이 지난 경우 당일 편입/연기 처리는 누가 결정하는가?
이유: 담당자 변경·오늘 일정·미처리 목록의 상태를 설명.
연결: F07/F08.
답에 따른 변경: 수락 결과의 선택 옵션·날짜 설명.
임시 가정: 당일 지도 편입은 수신자의 명시 선택.
미답변 시 보류: 자동 일정 변경·자동 편입. Q4 답으로 해결되면 묶어서 처리.

Q8 [알림 정책] 팀 알림·팀원 활동 알림은 어떤 이벤트를 뜻하며 끌 수 없는 필수 업무 알림이 있는가?
이유: 효과 없는 스위치를 실제 수신 제어로 연결할 때 필요.
연결: F01/F11.
