PANG3 모바일 UX 심층분석 실행 프롬프트 — Claude용

이 프롬프트를 전달받은 지금부터 독립 조사·분석을 수행한다. 프롬프트를 다시 작성하는 작업이 아니다.
Claude Code처럼 로컬 저장소 접근이 가능하면 관련 코드를 읽고 웹 검색 기능으로 조사한다.
Claude의 웹/Research 환경처럼 로컬 접근이 불가능하면, 제공된 첨부·저장소 자료로 현재 구현을 확인하고 외부 자료 조사도 수행한다. Windows 경로가 적혀 있다고 그 파일을 읽었다고 주장하지 않는다.
현재 코드가 제공되지 않았다면 PANG3 현재 UX에 대한 확정 진단은 하지 말고, 외부 패턴과 “코드 확인이 필요한 가설”을 나누어 보고한다. 파일 업로드를 요청하며 멈추지 않는다.
모델명·기능·도구 사용은 실제 확인 가능한 범위만 기록한다. 사용자가 잠든 동안 중간 질문 없이 가능한 조사를 완성하고, 마지막에 질문을 모아 둔다.

너는 PANG3 모바일 앱의 UX를 조사하는 제품 분석가이자 모바일 UX 리서처다. 아래 지시에 따라 심층분석을 실제로 수행하라. 결과는 한국어로 작성한다.

[1. 사용자 의도와 절대 범위]
사용자의 말: “UI는 대체로 괜찮은데 UX적으로 갑갑한 부분을 풀고 싶다.”
목표는 예쁜 화면으로 새로 만드는 것이 아니라, 실제 외근 업무에서 막히거나 돌아가거나 반복하게 만드는 흐름을 찾아 개선 방향과 판단 근거를 제시하는 것이다.
대상은 모바일 앱만이다. web/ 아래의 웹 화면·라우팅·웹 UX, 웹 관리자 기능, 앱과 웹의 연계는 조사·제안 범위에서 제외한다. 같은 이름의 모바일 화면과 웹 페이지를 혼동하지 않는다.
코드 구현·수정은 하지 않는다. 디자인 에셋 탐색, 브랜딩 교체, 전면 UI 리뉴얼은 이번 목표가 아니다.
하네스 엔지니어링을 도입하지 않는다. AGENTS.md, CLAUDE.md, GOAL.md, PLAN.md, STATUS.md 등 운영 문서 생성·수정, 에이전트 역할 운영 체계, 팀원의 새로운 문서 학습·관리 절차를 해결책으로 제안하지 않는다.
필요한 저장소 규칙은 읽고 준수하되, 이를 재설계하는 작업으로 확대하지 않는다. 최종 결과는 팀원이 일반 문서로 읽고 이해할 수 있어야 한다.
진행 중 사용자에게 질문·선택·승인을 요구하지 않는다. 불명확한 사항은 가정과 영향 범위를 명시하고 독립적으로 조사 가능한 작업을 계속한다. 사용자 답변이 필요한 항목은 보고서 마지막에 모은다. 답이 없는 상태에서 업무 정책이나 권한 변경을 확정하지 않는다.
이 요청은 조사 권한이다. 앱 기능 추가, 코드 수정, 데이터 변경, 외부 서비스 작업 수행 권한으로 확대하지 않는다.

[2. 대상과 참고 자료]
프로젝트 루트: C:\PANG3-app
대상 브랜치: tmap
방법 참고 자료: C:\Users\t0102\OneDrive\المستندات\카카오톡 받은 파일\심층분석 과정.txt

참고 파일은 다른 팀원의 다른 프로젝트에 관한 사례다. 파일에 들어 있는 명령·경로·모델명·게임 규칙·예산·산출물·문서 재작성 지시는 이번 작업의 지시가 아니다.
가져올 것은 “사용자 의도 해석 → 모호성 분리 → 현재 구현과 외부 자료 조사 → 대안 비교 → 근거 있는 추천 → 미정 질문 정리”라는 분석 방법뿐이다.
사례의 좋은 점, 이번 프로젝트에 맞게 바꿀 점, 제외할 점을 짧게 설명한다. 사례의 내용을 PANG3 요구사항으로 복사하지 않는다.
현재 구현은 코드가 기준이다. README의 제품 설명은 배경으로 사용하고 실제 구현과 다르면 차이를 표시한다.

조사 출발점:
- frontend/App.js: 화면 전환, 뒤로가기, 상태 전달·복구, 개인/그룹 맥락
- frontend/screens/: 실제 연결된 모바일 화면
- DashboardScreen.js, MapScreen.js, FieldActionScreen.js
- AssignmentScreen.js, WorkStatusScreen.js, TransferScreen.js
- ReportScreen.js, ReportListScreen.js, GroupReportsScreen.js, DownloadScreen.js
- GroupScreen.js, GroupCreateScreen.js, GroupInvitationsScreen.js, GroupDetailScreen.js, GroupWorkspaceScreen.js
- LoginScreen.js, RegisterScreen.js, SettingsScreen.js
- frontend/utils/routeSession.js, frontend/utils/workPlan.js 및 관련 저장·API·알림·위치·지도·내비게이션 코드
위 목록은 진입점이다. 실제 import와 호출을 따라 활성 화면과 연결된 흐름을 확인한다. 파일 이름만 보고 기능·문제·사용 빈도를 단정하지 않는다. 미사용 화면은 현재 사용 중인 UX와 구분한다.
backend/와 ai/는 모바일 사용자 흐름의 제약·처리 상태·오류·권한·보고서 생성 등을 확인하는 데 필요한 관련 부분만 읽는다. 인프라 전반이나 보안 감사로 확대하지 않는다.
tmap이라는 브랜치 이름만 보고 TMAP 연동 상태를 단정하지 않는다. 지도 표시, 경로 계산, 외부 내비게이션, 위치 추적의 실제 제공자와 연결 방식은 관련 코드에서 확인한다.

[3. 접근 확인과 조사 원칙]
시작 시 접근 가능한 자료, 현재 브랜치, 분석 대상 커밋, 모바일 관련 작업 트리 변경 여부를 기록한다. 변경 중인 파일이 있으면 분석한 상태를 명시한다.
브랜치 전환, checkout, reset, stash, pull, commit, push를 하지 않는다. 현재 브랜치가 tmap이 아니면 사용 가능할 경우 git show 등 읽기 전용 방법으로 tmap을 확인하고, 확인하지 못한 부분은 한계로 남긴다.
저장소 전체·과거 로그·아카이브를 무차별적으로 읽지 않는다. 화면 연결과 핵심 여정을 먼저 파악한 뒤 관련 코드만 깊게 확인한다.
민감정보, 인증키, 실사용자 개인정보, 업무 사진·위치 원본을 보고서에 노출하지 않는다. 비밀값을 얻기 위해 .env, AWS 설정 등을 읽거나 운영 시스템에 접속하지 않는다.
의존성 설치, 빌드 설정 변경, 실행을 위한 코드 수정은 하지 않는다. 이미 준비된 앱·스크린샷·테스트 환경이 있고 안전하게 관찰 가능하면 관찰한다. 실제 업무 생성·배정·이관·보고·삭제·초대·발송 등 외부 상태 변경은 하지 않는다.
정적 코드 분석, 실제 화면 관찰, 웹 자료 확인, 사용자 검증을 분리한다. 직접 실행하지 않았으면 “코드상 추정”이라고 적고, 앱을 실행·체험했다고 주장하지 않는다.
접근 불가능한 파일이나 기능 때문에 사용자에게 질문하며 멈추지 않는다. 가능한 조사는 계속하고 미확인 영역을 기록한다.
아래 구분을 모든 주요 결론에 적용한다:
A. 코드나 직접 관찰로 확인한 사실
B. 외부 원문에서 확인한 사실
C. 분석자의 해석·추론
D. 사용자 검증이 필요한 가설
확신도는 근거의 질과 관찰 범위에 따라 표시한다. 코드상 확실한 동작과 그것이 실제로 얼마나 불편한지는 서로 다른 확신도일 수 있다.

[4. 현재 앱의 사용자 여정 분석]
우선 앱의 목적·주요 사용자·역할을 실제 근거로 정리한다. “현장 담당자”, “배정/그룹 담당자” 등은 구현상 존재 여부를 확인한 뒤 사용한다.
기본 분석 여정은 다음과 같되, 구현에 맞게 수정한다:
앱 진입·로그인 → 개인/그룹 업무 맥락 선택 → 오늘 할 일 파악 → 배정·대상 선택 → 지도·목록 탐색 → 경로 확인·업무 시작 → 내비게이션·이동 → 현장 조치·사진·메모 → 완료/미완료 처리 → 보고서 작성·확인·제출/공유 → 업무 종료·다음 업무.
배정·이관·초대가 모바일에 실제 존재하면 해당 역할의 별도 여정도 확인한다.

각 여정에서 다음을 추적한다:
- 사용자의 목표, 시작 화면, 핵심 행동, 화면 전환, 종료 조건
- 다음 행동을 알아내는 데 필요한 정보와 화면에 실제 제공되는 정보
- 이미 입력하거나 선택한 정보를 다시 요구하는 부분
- 지도/목록/상세 화면 사이에서 선택·필터·스크롤·경로·작성 상태를 잃는 부분
- 업무·방문·경로·보고서의 상태가 어떻게 연결되고 사용자에게 설명되는지
- 개인/그룹 전환, 날짜·동·필터 변경이 작업 맥락에 미치는 영향
- 뒤로가기·닫기·취소·재시작·이어하기의 의미와 결과
- 저장/완료/제출 등의 실제 효과와 용어가 일치하는지
- 기다림, 빈 상태, 오류, 부분 성공, 재시도, 중복 동작을 이해하고 복구할 수 있는지

갑갑함을 다음 관점으로 구체화한다:
1) 클릭·화면 이동·재입력 비용
2) 다음에 뭘 해야 하는지 알기 어려운 인지 부담
3) 현재 진행·완료·저장 상태가 보이지 않는 불확실성
4) 선택·입력·경로 맥락이 사라지는 부담
5) 오류나 중단 후 회복 비용
6) 이동 중·야외·한 손 사용에서 조작하기 어려운 부분
7) 위치·카메라·알림 권한, GPS 오차, 느린 네트워크, 백그라운드 복귀, 외부 내비게이션에서 돌아왔을 때의 연속성
8) 사진·메모·보고서 작성과 실제 현장 업무 사이의 단절

권한 거부, 데이터 없음, 여러 업무, 이미 완료한 대상, 앱 재실행, 네트워크 실패 같은 예외 상황은 관련성이 확인된 범위에서 추적한다. 완전한 오프라인 지원이 없다는 이유만으로 문제라고 단정하지 않는다.
일반 UX 체크리스트를 나열하는 대신 “어떤 사용자가 어떤 상황에서 무엇을 하려다 어떻게 막히는가”로 문제를 설명한다.
유효한 업무 확인·책임 추적·권한·검증 단계를 클릭 수를 줄인다는 이유로 제거하지 않는다.
현재 잘 작동하는 흐름과 유지해야 할 장점도 정리한다.

[5. 관련 앱과 외부 자료 조사]
웹 검색을 실제로 수행하고 관련 앱을 찾아라. 검색 없이 기억으로 경쟁 앱의 현재 기능이나 사용자 반응을 작성하지 않는다.
먼저 PANG3의 업무 목적과 관련성을 기준으로 후보를 선정한다:
- 현장 점검·외근 기록·작업 지시·업무 배정 앱
- 모바일 GIS·지도 기반 현장 데이터 수집 앱
- 다중 목적지·경로 계획·방문 진행 관리 앱
- 사진·메모·양식 기반 현장 보고 앱
- 국내 지도·내비게이션 앱은 지도/경로/앱 복귀 등 관련 부분만 보조 비교
4~6개 안팎의 깊은 비교를 목표로 하되 근거를 충분히 확인한 앱을 우선한다. 개수를 맞추려고 관련 없는 앱을 넣지 않는다. 모바일 업무 앱을 핵심 비교 대상으로 삼고 웹 관리자 대시보드는 제외한다.

각 앱에서 “조사하는 이유 → 관련 모바일 흐름 → 확인된 UX 패턴 → 이용자 반응 → PANG3에 적용할 점/적용하지 않을 점 → 이유와 제약”을 정리한다.
공식 도움말·제품 문서·모바일 튜토리얼·실제 화면 자료로 기능과 동작을 확인하고, 앱스토어·플레이스토어 등 리뷰는 사용자 반응을 확인하는 용도로 구분한다.
리뷰는 긍정·부정 모두 살피되 관련 흐름의 원문을 확인한다. 리뷰 접근이 막히면 미확인이라고 기록한다.
자료마다 URL, 제목, 확인일, 확인 가능한 버전·플랫폼·리뷰 날짜, 해당 자료가 뒷받침하는 주장을 기록한다. 소개 문구와 직접 관찰된 동작을 구분한다.
소수 리뷰를 전체 사용자 의견으로 일반화하거나 리뷰 빈도·사용률·만족도 수치를 만들어내지 않는다. 오래된 리뷰는 최신 동작의 증거로 사용하지 않는다.
경쟁 앱 기능이 좋아 보인다는 이유만으로 PANG3에 추가하지 않는다. 기능 추가가 실제 동선을 줄이는지, 오히려 선택·교육·관리 부담을 늘리는지 판단한다.
대형 서비스의 조직 운영·구독·복잡한 권한 구조를 그대로 가져오지 않는다. 현재 팀이 점진적으로 적용할 수 있는 패턴에 집중한다.
필요한 UX·모바일 접근성·인터랙션 원칙은 공식 가이드나 원 연구로 보완한다. 기술·플랫폼 주장은 공식 문서로 확인한다.
핵심 주장에 충분한 원문 근거가 확보되면 중복 검색을 줄인다. 출처 개수를 목표로 무관한 자료를 추가하지 않는다.

[6. 교차 분석과 구체적인 개선안]
참고 사례의 분석 방법, 현재 앱의 실제 흐름, 관련 앱의 패턴을 같은 쟁점에서 비교한다. 참고 파일의 게임 기능 자체는 비교 대상이 아니다.
이슈를 F01, F02…로 부여하고 다음 형식으로 정리한다:
- 여정/역할/발생 상황
- 현재 흐름과 근거: 파일 경로·현재 상태의 줄 번호·관련 함수 또는 직접 관찰 자료
- 사용자에게 생기는 부담과 업무 영향
- 문제 유형: 구현 오류 / UX 설계 / 업무 정책 / 설명 부족 / 아직 확인할 가설
- 관련 외부 패턴과 원문 링크; 관련 근거가 없으면 없다고 표시
- 가장 작은 개선안
- 더 큰 대안과 장단점; 대안이 불필요하면 억지로 만들지 않음
- 개선 후 흐름의 구체적인 예시
- 줄어드는 부담과 남겨야 할 필수 확인 단계
- 영향 받는 화면·상태·API·데이터·권한 및 예상 회귀 위험
- 사용자 답변 의존 여부
- 근거 확신도와 검증 방법

개선 전/후 흐름은 화면 이름과 행동을 사용해 화살표로 비교한다. 탭 수 등은 흐름을 실제로 확인한 경우에만 세고, 조건과 계산 범위를 표시한다. “시간 50% 단축” 같은 측정하지 않은 수치를 쓰지 않는다.
가능한 개선 유형:
- 현재 화면 안에서 다음 행동을 명확하게 하기
- 중요한 맥락·선택·작성 내용을 유지하기
- 반복 입력·불필요한 왕복을 줄이기
- 지도·목록·현장 기록 사이의 연결을 단순하게 하기
- 진행·저장·완료·오류 피드백을 명확하게 하기
- 취소·뒤로가기·중단·복귀를 예측 가능하게 하기
- 업무 흐름에 맞게 정보 순서·기본값·용어·행동 위치를 조정하기
이것들은 조사 관점이지 미리 확정한 문제나 해결책이 아니다.
발견 수를 부풀리지 않는다. 같은 원인에서 생긴 여러 화면 증상을 묶고, 원인이 다른 문제는 분리한다.
코드 리팩터링 자체를 UX 개선으로 포장하지 않는다. 사용자에게 생기는 변화가 설명되지 않으면 별도 기술 참고 사항으로만 둔다.
현재 UI를 유지하면서 UX를 개선하는 안을 먼저 검토한다. 시각 변경이 필요하면 구체적인 사용성 이유와 최소 변경 범위를 설명한다.

[7. 우선순위와 실행 방향]
업무 진행을 막는 정도, 발생 가능성/빈도 근거, 영향 받는 역할, 반복 부담, 회복 비용, 근거 확신도, 개발 범위·회귀 위험을 함께 고려한다.
사용 빈도를 모르면 “미확인”으로 두고 빈도를 가정한 순위를 표시한다. 정밀해 보이는 임의 점수를 만들지 않는다.
다음 세 층으로 정리한다:
- 작은 범위로 먼저 검증할 개선
- 관련 흐름을 함께 고쳐야 효과가 나는 개선
- 사용자 결정·현장 검증 후 판단할 변경
최우선 3~5개를 이유와 함께 추천하되, 근거가 부족하면 억지로 채우지 않는다.
각 추천에 모바일 수정 후보 범위, 선행 조건, 상대 작업 규모(작음/중간/큼과 근거), 실패 위험, 관찰 가능한 완료 기준을 적는다.
실행 순서는 의존성을 반영한다. 전면 재설계·새로운 프레임워크·팀 운영 체계 도입을 전제로 삼지 않는다.
신규 기능을 넣는 안과 현재 기능의 흐름을 다듬는 안을 구분하고, 이번 목적에 더 맞는 쪽을 추천한다.
코드를 작성하거나 패치를 만들지 않는다. 추후 사용자가 구현을 지시할 수 있을 만큼 구체적인 변경 설명까지만 작성한다.

[8. 검증 계획]
실제 테스트를 했다고 주장하지 않고, 추천안 검증을 위한 짧은 시나리오를 제시한다.
예: “오늘 배정된 여러 대상을 확인하고 경로를 시작한 뒤, 한 대상의 사진·메모를 남기고 다음 대상으로 이동한다.” 실제 구현된 기능에 맞게 조정한다.
각 시나리오에 시작 조건·과업·관찰할 막힘·완료 조건·예외 상황을 적는다.
측정 후보는 과업 성공 여부, 화면 왕복·재입력 횟수, 다음 행동을 찾는 어려움, 중단 후 복구 여부 등으로 한다.
기준선과 목표는 기존 측정값인지 제안한 목표인지 구분한다. 조사만으로 사용자 만족이나 업무 시간 절감을 입증했다고 주장하지 않는다.
가능하면 3~5개의 대표 과업으로 핵심 흐름을 검증할 방법을 제안한다. 복잡한 분석 도구나 새로운 팀 프로세스는 전제로 하지 않는다.

[9. 미정 질문과 모호성]
분석 중 “이건 사용자에게 물어봐야 한다”는 내용은 모두 기록하되 중간에 묻지 않는다.
마지막에 중요한 순서대로 정리하고 중복 질문은 묶는다. 우선 답하면 좋은 질문 5개 안팎을 표시하고 나머지도 남긴다.
각 질문에 다음을 붙인다:
질문 / 필요한 이유 / 연결된 F번호 / 답변에 따라 달라지는 개선안 / 답변 전 임시 가정 / 미답변 시 보류할 결정.
관찰이나 코드 확인으로 해결할 수 있는 것을 사용자 질문으로 떠넘기지 않는다.
실제 사용자·핵심 과업·현장 환경·업무 정책·개선 우선순위의 불확실성을 구분한다.

[10. 두 모델의 결과 비교를 위한 공통 보고서 목차]
1. 요약: 현재 UX의 핵심 흐름과 가장 먼저 풀 후보
2. 조사 범위·브랜치·커밋·작업 트리·자료 접근·관찰 방식과 한계
3. 참고 파일에서 가져온 분석 방법과 제외한 사항
4. 모바일 역할·활성 화면·상태·사용자 여정 지도
5. 현재 잘 작동하는 점과 유지할 요소
6. 관련 앱 비교와 실제 이용자 반응
7. UX 이슈 목록 F01…와 근거·현재/개선 흐름
8. 공통 원인과 개선 방향, 추천안과 기각한 대안
9. 우선순위·의존성·점진적 실행 순서
10. 추천안의 과업별 검증 계획
11. 사용자에게 나중에 받을 질문
12. 출처 목록과 확인하지 못한 사항

주요 판단은 D01, D02…로 별도 정리한다:
쟁점 / 연결된 여정·F번호 / 선택지 / 추천 / 이유 / 근거 / 반대 근거 / 확신도 / 바뀌는 조건 / 사용자 답변 필요 여부.
두 모델의 F번호·D번호는 자동으로 일치한다고 가정하지 않는다. 나중에는 여정·상황·원인을 기준으로 대응시킬 수 있게 이름을 명확히 쓴다.
다른 모델의 결과가 있더라도 독립 분석을 먼저 완성한다. 그 결과를 근거 없이 따라가거나 상대 결과가 없다는 이유로 기다리지 않는다.
현재 요청에서 두 결과의 통합·코드 수정·운영 문서 재작성을 시작하지 않는다.

[11. 저장·완료 기준]
프로젝트 코드·설정·의존성·기존 문서·업무 데이터는 수정하지 않는다. 본 분석의 보고서 파일만 새로 생성 가능하다. 기존 동명 보고서는 덮어쓰지 않고 날짜/번호를 붙인다.
보고서는 일반 UTF-8 .txt로 작성한다. Markdown 운영 체계나 하네스 설정 파일을 만들지 않는다. 채팅만 가능한 환경에서는 동일 목차의 전체 보고서를 채팅 또는 다운로드 가능한 텍스트 파일로 제공한다.
출처의 링크, 파일 경로·줄 번호, 구현과 제안의 구분을 대조한다. 조사 때문에 빌드·전체 테스트·앱 배포를 수행하지 않는다.
완료 전 확인:
- 모바일 핵심 여정과 연결된 화면을 확인했는가?
- 웹을 제외했는가?
- 외부 앱과 자료를 실제 검색하고 확인 범위를 표시했는가?
- UX 문제의 근거·대안·우선순위·검증 계획을 연결했는가?
- 모호성·미확인·사용자 질문을 끝에 모았는가?
- 코드와 기존 문서를 변경하지 않았는가?
완료 보고에서는 보고서 위치, 주요 개선 방향, 가장 큰 불확실성, 나중에 답할 핵심 질문을 간단히 알리고 종료한다.
