[1. 절대 변경할 수 없는 사용자 요구]

사용자 직접 요구: “작업 전/작업 중/작업후 이거는 못바꿔 그사람들이 이렇게해달라고했기때문에”.

- ‘작업 후’를 ‘완료’, ‘완료 보고’, ‘제출’ 등의 상태명으로 교체하지 않는다. 고정 명칭을 다시 선택해 달라고 질문하지 않는다.
- pending / working / complete의 기존 대응, 단계 순서, 기존 완료 기록의 수정 제한, 배정·접근권한을 임의 변경하지 않는다.

- ‘보고서 저장’의 실제 효과를 설명한다. 현재 구현에 없는 제출 API·승인 절차를 가정해 ‘완료로 제출’이라고 제안하지 않는다.

M11 캐시·새로고침 실패·빈 결과

M14 복귀 행동과 버튼 문구
Claude F09 / Codex F01·F10. 출발 화면·다음 화면·복귀 화면 표를 만들고 ‘홈으로 돌아가기’와 실제 goBack 불일치를 확인한다. 지도/그룹/보고서에서 시작한 흐름을 보존하는 최소 변경을 우선한다. 모든 history 초기화나 전체 탭 스택 재설계를 작은 수정처럼 제안하지 않는다.

M15 검색·기록 행동·미완성 메뉴
Codex F12 / Claude F12. 검색처럼 보이는 영역이 추가 메뉴를 여는 이유와 공공시설 진입을 함께 확인한다. 행동에 맞는 문구 또는 직접 주소 검색+명확한 추가 행동을 비교한다. 기록 진입을 발견하기 쉽게 한다. 미완성 Excel/사진 추가를 구현하는 것으로 확대하지 않는다. 터치 영역·라벨·글자 크기는 준비된 화면/실기기 검증 범위에서 판단한다.

M16 로그인 오류와 설정 저장의 실효성
Codex F11·F13 / Claude F13. 인증/네트워크/서버 오류를 구분하고 그룹 알림 설정의 실제 저장·효과를 확인한다. 지원이 없는 설정을 저장 성공으로 표시하지 않는다. 범위를 인증 체계 재설계로 넓히지 않는다.

M17 촬영 복구와 지속 초안
Codex의 단계적 보존 개선 / Claude D03. M02·M03와 별도 구조 안으로 평가한다. Expo v57 ImagePicker 공식 문서의 getPendingResultAsync는 Android Activity 종료 시 복구 경로다. 결과만으로 대상·사용자·사진 단계가 복원되는 것은 아니다.
공식 문서: https://docs.expo.dev/versions/v57.0.0/sdk/imagepicker/
촬영 요청 맥락, 사용자·그룹·업무 키, 로컬 파일 수명, 저장 공간, 로그아웃 정리, 서버 충돌과 소유권/완료 변경 검증을 포함한다. URI만 저장하면 지속 보존이 된다고 단정하지 않는다. 서버와 다른 초안을 조용히 삭제하지 않는다. 의존성 업그레이드를 전제로 하지 않는다.

M18 다음 업무 제안
Claude F06·D06. 작업 후 저장이 서버에서 확인된 경우 같은 맥락의 다음 후보와 수동 안내 시작을 제안하는 안을 평가한다. 작업 전/작업 중 저장에는 완료된 것처럼 진행하지 않는다. 보고서 출발 흐름의 복귀를 방해하지 않는다. 현재 거리 휴리스틱 추천을 도로 기준 최속이라고 표현하지 않는다. 경쟁 앱 원문이 접근 불가하면 코드 기반 가설로 명시한다.

M19 미연결 화면과 정책 경계

[6. 이미 발견된 상충·오류를 재도입하지 않기]

- Claude의 ‘작업 후 → 완료’ 및 ‘완료로 제출’은 채택하지 않는다.
- routeSession.js의 선행 보고서 행 번호가 파일 길이와 맞지 않을 수 있다. 최신 함수와 실제 위치를 재확인한다.
- 다른 RouteService 메서드의 OpenRouteService 호출을 현재 segment 안내 제공자와 혼동하지 않는다.

- 그룹 전환 시 초기화와 실제 영구 소실, 최신 기록 사진 누락과 파일 삭제를 구분한다.
- 임의 10초 기준, 업로드 n/N, 기대 효과 수치를 검증 사실처럼 사용하지 않는다.
- ‘취소는 원본 사용’, ‘index는 markerNumber’, ‘탭 이동은 history 초기화’ 같은 일괄 처방을 하지 않는다.
- Spoke 등 경쟁 사례 링크가 재확인되지 않으면 B 근거로 채택하지 않는다.

[7. 우선순위와 대안 비교]

각 항목마다 사용자 막힘 → 발생 조건 → 코드 근거 → 대안 최소 2개 → 추천 이유 → 의존성/위험 → 수용 기준 → 미확인 질문을 작성한다. 같은 문제를 여러 화면에서 발견해도 중복 집계하지 않는다.

A단계: 자료 손실·결과 오인 방지. M01~M04, M06.
B단계: 현장 여정 연결·복구. M05, M07~M16.
C단계: 구조·정책 검증. M17~M19와 AI 비동기 처리·개인 전체 이력·탭 스택 개편.

이 순서는 초기 추천이다. 최신 코드에서 이미 해결되었거나 다른 위험이 확인되면 근거를 적고 조정한다. 심각도, 빈도 추정의 불확실성, 핵심 여정 차단, 의존성, 변경 범위를 따로 평가한다. 확인되지 않은 사용자 빈도를 우선순위 숫자에 숨기지 않는다.

단순 문구/진입 개선, 여러 화면 상태 공유, API 계약 변경, 새로운 기능을 구분한다. backend 변경은 모바일 핵심 흐름에 필요한 좁은 범위로만 제안한다. 구현이 커진다는 이유만으로 필수 데이터 보존 문제를 문구로 덮지 않는다.

[8. 수용 기준과 사용자 검증 시나리오]

구현 가능한 수용 기준을 제시하되 이 조사에서 테스트를 실행했다고 주장하지 않는다. 준비된 테스트/관찰을 수행하면 환경과 결과를 별도 기록한다.

V01 사진 혼합 저장: 작업 전/중/후의 일부 기존 사진, 새 교체 사진, 빈 단계, 의도적 삭제를 조합한다. 저장 후 재조회 시 타입·슬롯·내용이 일치하고 과거 이력과 권한이 보존되는지 확인한다.
V02 기록 이탈: 메모·사진 변경 후 헤더/back/iOS swipe/탭/알림 이동을 각각 시도한다. 유지·이탈 선택, 저장 중 보호, 저장 후 불필요한 경고 여부를 확인한다.
V03 사진 편집: 새 사진 원본 사용·편집 완료·버리기, 기존 사진 편집 취소를 구분한다. Android 촬영 중 Activity 종료는 별도 실기기 복구 시나리오다.
V04 저장 결과: 작업 전/작업 중/작업 후, 네트워크 실패, HTTP 실패, 보고서 생성 실패/지연을 구분한다. 명칭 유지·제한 안내·입력 보존·중복 요청 방지·실제 성공 판단을 확인한다.
V05 도착 후 기록: 작업 시작 HTTP 성공/실패, 안내 종료 이벤트 순서, 기록 진입과 올바른 대상·그룹 연결을 확인한다.
V06 파일: 1건/N건 선택, 파일 없음/일부 없음, 미리보기 왕복·다운로드와 선택/필터/스크롤 복귀를 확인한다.
V07 업무 맥락: 개인↔그룹, 그룹 첫 진입, 경로 복구, 수락한 이관의 pending→오늘 업무 수동 편입, 알림의 삭제/권한 상실 대상을 확인한다.
V08 복구 가능성: 위치 거절·GPS 지연, 캐시 갱신 실패·실제 0건, 다건 추가 일부 성공·실패 건 재시도, 로그인 서버 오류를 확인한다.

현장 담당자 검증은 작은 과제 중심으로 설계한다. 무엇을 누를지 찾는 시간, 반복 행동, 누락/잘못 저장한 건, 복귀 성공, 다음 행동 이해를 관찰한다. 사전 값과 사후 값을 실제 측정하기 전에는 개선 퍼센트를 약속하지 않는다.
